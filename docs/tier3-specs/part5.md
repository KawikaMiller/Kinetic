**`simd-gpu-parallelism` · SIMD & GPU Parallelism**
Track `hw` · *"One instruction, many lanes"* · Builds on: none (soft links in words only to `cpu-pipelining`, `cpu-caches`, `amdahls-law`, all registered)
**Spec.**
- **Lanes scene.** An array of N 32-bit floats (default 20, learner field 1-64 via `parseBoundedInt`) and the loop `c[i] = a[i] + b[i]`.
  - A width picker: scalar (1 lane), 128-bit (4 lanes), 256-bit (8), 512-bit (16). Lanes = register bits / 32, shown as the division.
  - The array strip highlights the elements one instruction touches. Stepping shows `floor(N / W)` vector instructions and a **tail** of `N mod W` elements.
  - A tail picker: "scalar epilogue" (the leftover elements one by one, violet) or "masked tail" (one masked vector op with the unused lanes dimmed). N = 20 with W = 8 gives 2 vector ops plus a 4-element tail, which the learner can see is not free.
  - A **memory bandwidth** slider B (4, 8, 16, 32, 64 bytes per cycle; a toy). Each element moves 12 bytes (two loads, one store), so a vector op needs `ceil(12 * lanes / B)` cycles if memory is the limit. Cycles = `max(compute, memory)` and the stat names which one binds ("memory-bound: wider lanes stopped helping"). The sentence is derived from the two numbers, never scripted (AC-0/T3 #14).
- **Dependence scene.** The loop `a[i] = a[i - d] + 1` with a distance slider d (1-8) and the same width picker. The vector execution reads W elements, adds, then writes W elements, exactly as hardware would; the scalar loop is run beside it and the arrays are compared element by element.
  - A vector width W is legal only while W <= d. Beyond that the first mismatching index is ringed `--bad` and the lesson says which elements were read before they were written.
  - "Vectorisable" is computed by running both versions, not by a lookup of `W <= d`; the rule is the test's expected answer.
- **Warp scene.** 32 lanes drawn as a 4x8 grid (a phone-safe shape). Each lane has a predicate bit (a `BitStrip` toggle row: tap a lane to flip it; presets: all true, even lanes, one lane, first half) for `if (p) { A: 6 instructions } else { B: 4 instructions }`.
  - The warp issues path A with the true lanes active (others greyed `--dim`), then path B with the rest. Cost = A + B when both groups are non-empty, A or B alone otherwise. Utilisation = useful lane-slots / issued lane-slots.
  - A second program, `for (k = 0; k < n[lane]; k++) work`: each lane gets a trip count (seeded presets, editable); the warp runs until the longest lane is done, so utilisation = sum(n) / (32 * max n).
- **Latency-hiding scene.** A `createTickSim` (K3-2) with W resident warps, each alternating c compute ticks with a memory stall of L ticks (a toy, labelled), one issue slot per tick. Sliders: warps 1-16, stall L 10-100, compute c 1-8. A utilisation bar fills; the lane Gantt (`barAt`) shows which warp issues each tick. Utilisation = issued ticks / elapsed ticks.
- Presets: "image brighten (no dependence)", "prefix-sum written naively (d = 1)", "unlucky tail (N = 17)", "half the warp diverges".
- Real hardware facts, each chipped `from-memory`: 128/256/512-bit SIMD registers are SSE, AVX2 and AVX-512 on x86 (NEON is 128-bit on Arm); an NVIDIA warp is 32 threads; AMD's wavefront is 32 or 64 depending on the architecture. **Verify against** the Intel Intrinsics Guide, the CUDA Programming Guide and AMD's ISA documents.
**Out of scope.** Writing intrinsics, autovectorisation reports, memory coalescing and shared-memory banks (named in one caption), tensor cores, GPU memory hierarchy, the rendering pipeline (`gpu-rendering-pipeline`, wave 9).
**Kit.** `ArrayStrip` (cells with `cellState`, `ranges` for the vector window, `pointers`), `BitStrip` (predicate row with `ariaLabelOf` "lane 12 takes branch A"), `Segmented` (width, tail), `Slider` with `format`, `TextField` + `parseBoundedInt`, `Stat` (K3-3 multi-line sub for "memory-bound" reasoning), `createTickSim` and `useTickSim` (K3-2), `GanttLanes` + `barAt` (K3-10), `Plot2D` (utilisation against warps, one `Curve` per stall length), `CellGrid` (the 32-lane warp, `cell` tone per lane), `useScenePicker`, `ChipButton` presets, `Provenance`.
**AC.**
- **Watch:** an active lane is `--hi`; a lane masked off by divergence is `--dim`; elements handled by the scalar tail are `--violet`; a lane or element whose result differs from the scalar loop is `--bad`; a lane or element that matches is `--ok`; the binding resource (compute or memory) is `--info` on the stat that limits.
- **Misconception:** "a GPU thread is a fast little CPU thread" and "a wider vector is always faster". Quiz question: a loop reads and writes `a[i - 2]`; which width gives the right answer (and why not 4)? A second question: half the lanes of a warp take `else`; what does the warp pay?
- **Correctness:**
  - Vector cycles for every (N, W, tail mode) match a brute-force count of instructions emitted by a reference loop generator, for N = 1-64 and the four widths (256 cases).
  - The dependence verdict: for d = 1-8 and W in {1, 2, 4, 8, 16} on seeded arrays, the vector run equals the scalar run exactly when W <= d, and differs otherwise (all 40 combinations asserted); the first mismatch index equals the first element whose source was overwritten in the same chunk.
  - Divergence cost equals the number of instructions in the union of the lane traces: each lane's scalar trace is generated independently and the warp cost is the size of the merged lockstep trace (a hand-worked case: lanes {0..15} true gives 6 + 4 = 10, all true gives 6, none true gives 4).
  - The loop-trip-count utilisation equals `sum(n) / (32 * max n)` on seeded trip counts, and is 1 exactly when all counts are equal.
  - Latency hiding: tick-sim utilisation after warm-up is within 2% of `min(1, W * c / (c + L))` over a 4 x 4 x 4 grid of W, c, L; same seed gives the same history, and `at(k)` equals running k steps.
- **Hostile input:** N outside 1-64, decimals, `1e3` and empty are refused with the stated message and the old array kept. A trip-count field refuses negatives and anything over 64. A predicate row cannot be left in a state the model cannot run (all 32 combinations are valid).
- **Honesty:** `Provenance kind="toy"` on the cycle model ("one instruction per cycle, no pipelining, no cache; a roofline-style simplification"). `from-memory` chips on register widths and warp sizes. "A real GPU also hides latency with thousands of resident threads, not 16 warps; the numbers here only show the shape."

**Phone.** The array strip wraps by 8; the warp grid is 4 columns by 8 rows at 390 (cells 34px). Plot2D at 356 wide. No `minWidth` beyond the Gantt (`WideRegion minWidth={480}` for the issue timeline).

**`concurrency-models` · Concurrency Models: Threads, Async, Actors & CSP**
Track `os` · *"Four philosophies for doing many things at once"* · Builds on: `event-loop`
**Spec.**
- **One workload, four runtimes.** "Fetch R requests" (R slider 10-200, default 100), each needing a short CPU step then an I/O wait then a short CPU step. Illustrative constants, labelled: I/O wait 100 ms, CPU step 1 ms. Cores slider 1-8. The model is a deterministic discrete-event schedule that fills a `GanttLanes` timeline per model.
  - **OS threads:** one thread per request (or a pool of size P, a slider: P = R means "a thread each"). Memory = threads x an illustrative stack reservation (a named constant, 1 MB, hedged: "default stack sizes differ by OS and runtime; verify against your runtime's docs"), plus a count of times a thread blocks and is woken.
  - **Event loop:** one thread; I/O waits are callbacks. A "CPU hog" option makes request #7 spend 200 ms of CPU inside its handler.
  - **Actors:** each request is a message to one of A actors (A slider 1-16). One mailbox, one message at a time per actor; actors share nothing and talk by messages.
  - **CSP / channels:** W workers pull from a channel with buffer size K (0 = unbuffered, a rendezvous; the sender blocks until a worker is free).
- **Fault buttons:** "request 7 hogs the CPU for 200 ms" and "request 7 crashes". The model needs a decision table of what each runtime does by default (so it is tested and shown):
  - hog: threads, only that core is busy; event loop, **every other request waits** (the bystander latency stat jumps); actors, requests queued behind it in the same mailbox wait, other actors do not; CSP, one worker is busy, the rest keep going.
  - crash: a thread that dies from an uncaught exception ends that thread (Java); an unhandled rejection or exception in a Node callback ends the process unless handled; an unrecovered panic in a Go goroutine ends the whole program; a supervised actor (Erlang/Akka style) is restarted and its mailbox policy decides what survives. The table is chipped `from-memory`; **verify against** the Java, Node, Go and Erlang/OTP documentation. It is labelled "default behaviour", never "always".
- **Stats (K3-3 multi-line):** wall time, requests finished, peak concurrent threads or actors, illustrative memory, **bystander latency** (the finish time of the fastest request when the hog runs), and "context switches (toy)" counted by the model's own rule: threads, one switch per block and per wake on a core; event loop, 0 thread switches and R callbacks; the rule is shown beside the number.
- Preset chips: "100 URLs, 4 cores", "one slow handler", "one crash", "blocking call inside the event loop".
**Out of scope.** `event-loop` ordering rules (microtasks and macrotasks), `async-await-coroutines` mechanics, thread pool internals and work stealing (the next lesson), locks and `race-conditions`, distributed actors and supervision trees in depth.
**Kit.** `GanttLanes` (K3-10 `barAt` while it plays; kinds `work`, `wait`, `blocked`), `Segmented` (model), `Slider` ×4, `Toggle` (hog, crash), `Stat` (K3-3), `useScenePicker` for the fault state, `ChipButton` presets, `createRecorder` for the stepped frames, `Provenance`, `core/format` (`ms`, `bytes`, `plural`).
**AC.**
- **Watch:** CPU work is `--info`, an I/O wait is `--dim` hatched (`blocked`, not `wait`), a request delayed behind another is `--orange` (`wait`), the hog is `--bad`, a crashed worker is `--bad` with the restart in `--ok`, a bystander request that finished on time is `--ok`.
- **Misconception:** "async is faster than threads" and "an event loop uses many cores". Quiz: a handler spins the CPU for 200 ms in a single-threaded event loop; what happens to an unrelated 5 ms request?
- **Correctness:**
  - Makespan against a closed form: with P threads, R equal requests, I/O wait w and cores C >= P, makespan = `ceil(R / P) * (w + 2 * cpu)` (ignoring CPU contention), asserted for a grid; with C < P the CPU part is serialised and the test uses a brute-force list scheduler as the oracle.
  - The event-loop run equals a hand-written single-queue simulation; the hog adds exactly its 200 ms to every request that had not started its callback.
  - The decision table is asserted exhaustively over (model x fault x policy); no cell may be "undefined".
  - Memory = threads x stack constant; the statement "peak threads" equals the maximum concurrency read off the Gantt.
- **Hostile input:** R, P, A, W, K outside range are refused (sliders cannot leave range; typed fields refuse and keep the old value); an unbuffered channel with W = 0 workers is refused ("nobody to receive: the sender would block forever") rather than simulated into a stall.
- **Honesty:** `Provenance kind="illustrative"` on every constant (100 ms, 1 ms, 1 MB, 200 ms) and `from-memory` on the failure table. "Real thread switches cost microseconds and depend on the OS; the count here is a toy."

**Phone.** One model's timeline at a time via `Segmented` on ≤900px (the compare-all view is desktop); `WideRegion minWidth={520}` for the Gantt. Stats stack. Controls wrap.

**`thread-pools-work-stealing` · Thread Pools, Fork-Join & Work Stealing**
Track `os` · *"Keeping every core busy"* · Builds on: `concurrency-models` (earlier in this batch)
**Spec.**
- **Pool sizing scene.** A workload mix slider (CPU-bound to I/O-bound: fraction of time a task spends waiting, w/c ratio) and a pool-size slider. A tick sim (K3-2) runs T tasks on P threads and C cores and plots throughput against P (a `Curve` swept by the model, the learner's P marked by `VLine`).
  - CPU-bound peaks at P about C; blocking tasks keep gaining until P about `C * (1 + w/c)`, then flatten (a toy contention cost makes it fall slowly). The rule of thumb `N_threads = N_cpu * (1 + W/C)` is credited to *Java Concurrency in Practice*, chipped `from-memory`; **verify against** that book before naming it.
- **Fork-join scene.** A divide-and-conquer job: a task over a range of length n splits in two until the range is at most the **grain size** g (a slider), then runs `g` units of work.
  - Each of P workers (slider 1-8) owns a **deque**. The owner pushes and pops at one end (newest first, depth-first, cache-friendly); an idle worker **steals from the other end** (the oldest task, which tends to be the largest).
  - All work starts on worker 0 (the root task is submitted to one worker), which is what makes stealing visible. Controls: split ratio (50/50 down to 90/10, an unbalanced tree), grain size, P, steal on/off, seed.
  - Workers are `GanttLanes` lanes, a steal is a marked instant (K3-11 zero-length bar if built, else a marker), deques are drawn as stacks of task cards per worker. A utilisation bar and counters (steals, makespan, work T1, span T-infinity) fill as it plays.
- **Grain-size scene.** Each task has a spawn overhead (a named constant). Sweep g: a U-shaped makespan curve (too fine: overhead dominates and the run is slower than sequential; too coarse: idle workers). The learner's g is marked.
- **Starvation scene (fixed pool, blocking children).** A pool of P workers where each parent task blocks waiting for its two children without helping. With P small the pool reaches "every worker is waiting, queue not empty": the sim detects it deterministically and the stage says **stalled**, never "hung forever". A toggle "join by helping" (a waiting worker runs a queued task) fixes it. Chipped as simplified: real fork-join pools compensate or help; named, not modelled in depth.
**Out of scope.** Lock-free deque implementation (Chase-Lev) and memory ordering (named, one caption), NUMA and affinity, GPU scheduling, async runtimes' internals, Amdahl itself (`amdahls-law`).
**Kit.** `createTickSim` + `useTickSim` (K3-2), `GanttLanes` + `barAt` (K3-10; `barAt` for progressive bars) + the K3-11 instant, `Plot2D` (`Curve`, `VLine`, `Points`), `Bar` (utilisation), `Slider`, `Segmented`, `Toggle`, `Stat` (K3-3), `TreeSvg` (the task tree with `nodeMark` for which worker ran it, `hidden` for not-yet-spawned), `core/random mulberry32`, `Provenance`.
**AC.**
- **Watch:** each worker is a plain category (`orange`, `amber`, `pink`, `sky`, wrapping, never `--ok`/`--bad`), the tasks it ran keep its tone in the tree; a steal is `--info` (in flight) landing as the thief's tone; idle time is `--dim`; the stalled state and the slower-than-sequential run are `--bad`; the best grain in the sweep is `--ok`.
- **Misconception:** "more threads is always faster" and "work stealing means workers fight over one queue". Quiz: which end does a thief take from, and why the old end?
- **Correctness (independent oracle: the work-span bounds).**
  - Work is conserved: the multiset of leaf costs executed equals the multiset in the tree, for 200 seeded trees (random split ratios) and P = 1-8, with and without stealing.
  - Lower bound: `makespan >= max(T1 / P, T-infinity)` on every run, asserted with exact integer ticks.
  - With steals succeeding in the tick they are attempted (the lesson's model, stated), the scheduler is greedy and Brent's bound `makespan <= T1 / P + T-infinity` holds exactly (asserted); a broken variant with steal latency of k ticks must violate it on at least one seed (a named seed in the test), and the stage says which model it runs.
  - P = 1 with overhead 0 equals the sequential cost; with stealing off and all work on worker 0 the makespan equals T1 (the stage's "no stealing, no speedup" is computed).
  - The sizing curve peaks at P = C for CPU-bound tasks (w/c = 0) and the starvation scene reports `stalled` exactly when all workers wait and the queue is non-empty (asserted over a grid), never when helping is on.
- **Hostile input:** grain size below 1 or above n is clamped by the control's range, not by the model; P outside 1-8 refused; a seed field accepts a bounded integer only. Tasks with zero cost are refused (the model needs a positive cost).
- **Honesty:** `Provenance kind="simulated"` with the seed shown, `toy` on overheads, `from-memory` on the pool-sizing formula and on "real pools help or compensate".

**Phone.** Deques wrap under the Gantt; the Gantt scrolls (`WideRegion minWidth={560}`); the tree sits in its own region. P is capped at 6 on ≤600px to keep lanes readable (a stated limit, not silent).

**`parallel-patterns` · Parallel Patterns: Map, Reduce & Scan**
Track `os` · *"Thinking in data parallelism"* · Builds on: `simd-gpu-parallelism` (earlier in this batch)
**Spec.**
- **Input and operator.** The learner types up to 16 integers (`parseIntegers`, presets of 8 and 16) and picks an operator: `+`, `max`, string concatenation (digits as text), and **subtract**. A processors slider p (1-16) feeds the step estimates.
- **Map.** Every element is independent: one parallel step on enough processors; the strip shows all cells lighting together. Steps = `ceil(n / p)`.
- **Reduce.** Sequential fold (n - 1 steps) beside a **tree** (pair neighbours, halve the array each level: `ceil(log2 n)` levels, n - 1 operations in total). The tree result is compared with the sequential fold.
  - `+` and `max` agree. **Subtract** (not associative) and, with the "combine in arrival order" toggle, **concatenation** (associative but not commutative) are the failing states; the mismatch is shown with both numbers and the reason ("regrouping changes the answer" or "reordering changes the answer").
  - A floating-point preset (0.1, 0.2, 0.3 summed with different groupings) shows that even `+` on floats regroups to different bits; said in words, with the exact numbers computed in JS.
- **Scan (prefix sums).** Two algorithms with the same inputs:
  - **Hillis-Steele:** `ceil(log2 n)` steps, but about `n log n` additions (work-inefficient).
  - **Blelloch** (up-sweep then down-sweep, exclusive scan): about `2 (n - 1)` additions in `2 log2 n` steps for n a power of two (padded with the identity otherwise; the padding is drawn).
  - A `CellGrid` with one row per step and the columns as elements, `rowDecor` (K3-16) labelling "stride 2^k" or "up-sweep level k". An inclusive/exclusive toggle.
  - Counts shown as work (operations) and span (steps), and a Brent-style estimate `ceil(work / p)` to `work / p + span` for the chosen p.
- Preset chips: "sum of 8", "running max", "stream compaction by scan (keep the evens)" (a scan of 0/1 flags gives output indices; the compacted array is drawn), "histogram bucket offsets".
- Frameworks: a one-line note that map-reduce style systems need the combining function to be associative (and often commutative); chipped `from-memory`, **verify against** the Spark `reduce` documentation.
**Out of scope.** GPU implementations (bank conflicts, warp shuffles), segmented scans, MapReduce as a system (T3 `mapreduce-batch`, wave 5, linked only by words), parallel sorting, `amdahls-law`.
**Kit.** `ArrayStrip` (inputs and tree levels), `CellGrid` with K3-16 `rowDecor` (scan steps), `TextField` + `parseIntegers`, `Segmented` (operator, inclusive/exclusive), `Toggle` (arrival order), `Slider` (processors), `Stat` (work, span, steps), `createRecorder`, `GanttLanes` + `barAt` optional for the p-processor schedule, `Provenance`.
**AC.**
- **Watch:** operands being combined are `--info`, the partial result written this step `--hi`, a cell not touched this step `--dim`, the sequential-fold result `--ok` when the tree agrees and `--bad` on the tree's wrong value, the scan padding cells `--violet`.
- **Misconception:** "any operator can be reduced in parallel" and "parallel prefix sum does the same work as the loop". Quiz: reduce `[8, 4, 2]` with subtract as a tree and as a fold; which is "right"?
- **Correctness:**
  - The scan equals the sequential prefix computation for 2,000 seeded arrays of length 1-16, for `+`, `max`, concat, in both algorithms, inclusive and exclusive.
  - Tree reduce equals the fold for `+` and `max` on all arrays up to length 12 and **differs** for subtract on at least one named array; for concatenation it equals the fold in order and differs under every non-identity permutation of a three-element array (exhaustive over the 6 permutations).
  - Operation counts equal an instrumented count: Hillis-Steele additions = `sum over d of (n - 2^d)` for `2^d < n`; Blelloch up-sweep n - 1 plus down-sweep n - 1 for n = 2^k; **verify against** Blelloch's 1990 report or GPU Gems 3 chapter 39 before the numbers are quoted.
  - The step count is `ceil(log2 n)` for the tree and Hillis-Steele and `2 log2 n` for Blelloch (asserted for n = 1-16, padded).
- **Hostile input:** non-integers, empty list, more than 16 values and values beyond ±9,999 refused with the message; the old array kept. Concatenation treats values as digit strings and refuses negatives in that mode.
- **Honesty:** "Steps are model steps; real hardware has p fixed by the machine and memory costs the model ignores." `Provenance kind="toy"`.

**Phone.** 16 cells use `cellMax` and `size="sm"`; the scan grid scrolls inside a `WideRegion minWidth={460}` with the row labels pinned.

**`priority-inversion` · Priority Inversion**
Track `os` · *"When low priority blocks high"* · Builds on: `cpu-scheduling` · **[domain review]**
**Spec.**
- **Scheduler.** A single core with fixed-priority preemptive scheduling: the highest-priority runnable task runs. Three tasks H, M, L (priorities 3, 2, 1) and one mutex R shared by H and L. Each task is a script of segments: `compute(n)`, `lock(R)`, `unlock(R)`.
- **Editable scenario** (all as sliders and steppers, in ticks): L's critical-section length, H's arrival time, M's arrival time and compute length, and a **deadline marker** for H. A protocol picker: **none**, **priority inheritance**, **priority ceiling** (immediate ceiling).
- **Timeline.** `GanttLanes` with `barAt` (K3-10): lanes H, M, L. Kinds: `work` (running), `wait` (ready, preempted), `blocked` (H waiting for R, dashed). Bars that hold R carry `ring: 'violet'`. The effective priority of the running task is the bar label ("L as 3"). A deadline marker, and a shaded **inversion window** (the interval in which H is blocked and a lower-priority task other than the lock holder runs).
- **The story the learner reproduces:**
  1. L takes R. H arrives and blocks on R.
  2. With **none**, M arrives, outranks L and runs; H waits for M too, and **lengthening M's compute lengthens H's wait without bound**. H misses its deadline.
  3. With **inheritance**, L runs at H's priority while it holds R, M cannot preempt it, L releases R, drops back, H runs. H's blocking is at most L's critical-section length.
  4. With **ceiling**, L runs at the lock's ceiling (the highest priority of any task that uses R) from the moment it locks, so H never blocks on R at all once it starts later (it is delayed at most once, before it can lock).
- **Pathfinder scene (watchdog).** A preset named "Mars Pathfinder, simplified" renames the tasks (bus management high, communications medium, meteorological data low) and adds a **watchdog**: if H is blocked longer than a threshold the system resets (a `--bad` event). Enabling inheritance (the real fix was turning on the priority-inheritance option of the mutex) removes the resets. The whole scene is chipped `from-memory` and "simplified"; **verify against** Glenn Reeves' account of the 1997 mission and the VxWorks documentation of its inversion-safe mutex option before any sentence about the real event is shipped. No claim about which task did what beyond that account.
- Caveats shown as chips, not hidden: inheritance does not prevent deadlock (a second lock taken in the opposite order still deadlocks), chained blocking exists with several locks, and POSIX exposes the two protocols as mutex attributes (`PTHREAD_PRIO_INHERIT`, `PTHREAD_PRIO_PROTECT`); Linux futex-based PI mutexes exist (**verify against** the pthreads and kernel documentation).
**Out of scope.** Real-time schedulability analysis (rate-monotonic, response-time analysis), multicore priority inversion, lock-free alternatives, RTOS configuration. Round robin and MLFQ stay in `cpu-scheduling` (its Out of scope line gives priority inversion to this lesson).
**Kit.** `GanttLanes` (`kind`, `ring`, `markers`, `now`), `core/gantt` `barAt` (K3-10), `Segmented` (protocol), `Slider` ×5 with `format`, `ChipButton` presets, `Stat` (H's blocking time, H finish, deadline slack), `createRecorder` for stepped replays, `Provenance`, `Toggle` (watchdog).
**AC.**
- **Watch:** priority lanes are plain categories (`pink` H, `amber` M, `sky` L), never status colours; the lock-holding segment is ringed `--violet`; H's blocked time is dashed `--orange`; the **inversion window** is a `--bad` band; an inherited priority label is `--info`; a met deadline is `--ok`, a missed deadline or a watchdog reset `--bad`.

**Out of scope.** Memory-corruption exploitation, aliasing rules and `restrict` in depth (`compiler-optimisations`, same wave, words only), data races as UB (`race-conditions`), sanitizers' internals, the full C undefined-behaviour list (the lesson says the standard's list is long and names the usual suspects only).

  - Error ordering: on 2,000 seeded runs of the "one large then small" generator Kahan's error is no larger than naive's (a property, with the blind-spot generator named as the documented exception).
  - float32 emulation: `Math.fround` after each add equals a float32 sum done through `Float32Array` stores for 1,000 seeded sums; the lesson's double-then-round path is noted as innocuous for `+ - * / sqrt` because 53 >= 2 * 24 + 2 (**verify against** the double-rounding literature before the sentence ships).
  - Cancellation: the oracle is a BigInt integer square root at 80 digits, **not** the rewritten formula; "digits correct" is computed from the relative error against it and capped at 16. At `x = 10^16` the naive result is 0 (0 digits), the stable one agrees to 15 or more.

**`branch-prediction` · Branch Prediction & Speculative Execution**
Track `hw` · *"The CPU guesses, and sometimes pays"* · Builds on: `cpu-pipelining` · **[domain review]**
Fence quoted from `cpu-pipelining`: *"Branch prediction and speculation (T3 branch-prediction), superscalar and out-of-order execution (one summary line)."* The Tier 2 lesson stops at "a taken branch resolved in EX throws away 2 instructions"; this lesson asks how the CPU decides what to fetch before the branch resolves.
**Spec.**
- **Predictor lab.** A branch outcome stream (T/N) drawn as a row of cells, a **pattern row** the learner edits (a 16-cell `BitStrip` of toggles that repeats), and presets: *always taken*, *alternating TN*, *loop of four (TTTN)*, *random with probability p* (slider), *sorted data*, *unsorted data*. - **Sorted versus unsorted scene.** 256 seeded values in 0-255 and the loop `if (x >= 128) sum += x`. **`cache-coherence` · Cache Coherence (MESI) & False Sharing**
Track `hw` · *"When cores fight over a cache line"* · Builds on: `race-conditions` · **[domain review]**
Fence quoted from `cpu-caches`: *"Coherence between cores and false sharing (T3 cache-coherence), prefetchers (one honesty line), and TLBs."* Tier 2 teaches one core's cache and 64-byte lines; this lesson starts when there are several.
**Spec.**
- **MESI scene.** Four cores, each with a private cache holding one line `X` (the single line is drawn big; a `CellGrid` with K3-16 `rowDecor` gives each core a labelled row with a state rail), a shared bus, and memory. The learner presses **Read** or **Write** on any core. A write carries a value (a counter that increments) so that stale data is visible. States: **M**odified, **E**xclusive, **S**hared, **I**nvalid.
  - **Rules (write-invalidate snooping, as in the textbook protocol):**
    - *Read hit* in M, E or S: no bus traffic, no state change.
    - *Read miss*: a bus read. If another cache holds M it supplies the data and writes it back to memory, and both become S; if others hold E or S, they supply it and every holder is S; if nobody has it, memory supplies it and the reader becomes E.
    - *Write* in M: stays M. In E: becomes M silently. In S: a bus upgrade invalidates the other copies, then M. In I: a bus read-for-ownership (the "write miss") fetches the line and invalidates every other copy, then M.
    - *Snooped bus read*: M becomes S (after the write-back), E becomes S, S stays S. *Snooped read-for-ownership or upgrade*: any copy becomes I (M writes back first).
  - Each press shows the bus transaction, which caches reacted, the new state of every core and memory's value (stale while a line is M). A counter totals bus transactions.
  - A toggle **"turn off invalidation"** (the broken protocol): a write no longer invalidates other copies, and the next read on another core returns the **old value** (`--bad`), which the model produces; the stage says so.
- **False-sharing scene.** Two threads on two cores, each repeatedly incrementing **its own** counter. A layout picker: *two counters in one 64-byte line* (byte offsets editable, 0-127), *padded to separate lines*, *one shared atomic counter*, *per-thread counters merged at the end*. A line-size toggle (64 or 128 bytes).
  - An interleaving picker (strict alternation, bursts of k writes) and a run length. The model runs the MESI machine on the two cores' lines and reports **ownership transfers** (bus read-for-ownership and upgrade count) and **cost = transfers x T + hits x 1** (T a toy, default 100 cycles, labelled).
  - The result the learner reproduces: adjacent counters ping-pong the line on every alternation although they never touch the same variable; padding removes the traffic; a **truly shared** counter still ping-pongs when padded (padding fixes false sharing, not sharing), and per-thread counters plus a merge avoid it.
  - A `Plot2D` of cost against burst length shows the effect shrinking as writes batch.
- Real systems, chipped `from-memory`: Intel uses a MESIF variant and AMD a MOESI variant; large machines use directory protocols; many x86 CPUs have 64-byte lines and some Apple Arm designs are reported to use 128. Language support for padding exists (`alignas(64)`, C++17 `std::hardware_destructive_interference_size`, Java's `@Contended`). **Verify each against** the vendor manuals and language references.
**Out of scope.** Store buffers, memory-ordering models and fences (the model's bus transactions are atomic; a caption says real cores reorder), cache associativity and replacement (`cpu-caches`), NUMA, the details of directory protocols, atomics' instruction sequences.
**Kit.** `CellGrid` with K3-16 `rowDecor` (a rail per core, tone from the MESI state), `Flyer` or `Packet` for the bus transaction, `Segmented` (layout, line size, interleave), `Slider` (offsets, burst, length), `Toggle` (invalidation), `Stat` (bus transactions, transfers, cost), `Plot2D`, `createRecorder`, `GanttLanes` (one lane per core, `barAt`-style progressive when playing writes; optional), `Provenance`.
**AC.**
- **Watch (MESI colours are a fixed category map, stated in `watch`):** **M** is `--bad` (the only up-to-date copy, and the costly one to share), **E** is `--ok`, **S** is `--info`, **I** is `--dim`. The core acting now is ringed `--hi`; the bus transaction in flight is `--violet`; a stale read is `--bad` with "stale"; a line transfer counts as the costly side of the comparison in `--bad` on the cost stat, the padded layout's `--ok`.
- **Misconception:** "padding fixes any slow shared counter" and "the cache always has the latest value". Quiz: two threads each increment their own counter, stored side by side; why is it slow? A second: after core 2 writes, what state is core 1's copy of the line in?
- **Correctness (independent oracle: exhaustive invariants over all short operation sequences).**
  - **Exhaustive check:** all sequences of up to 6 operations over 4 cores (8 operations, about 262,000 sequences) are run and these hold after **every** step: at most one cache holds M or E, and then every other cache is I (single writer or many readers); if any cache is S then every valid copy equals memory; every read returns the value of the latest write (coherence).
  - The broken protocol (no invalidation) **must violate** the read-returns-latest-write invariant, and the test names the shortest violating sequence (write on core 0, read on core 1, write on core 0, read on core 1).
  - Hand-worked transitions: Read on I with no sharers gives E; a second core's read gives S and S; a write on S gives M and I; write on E is silent (0 bus transactions); a read of an M line writes back.
  - False sharing counts equal analytic values: strict alternation of n writes on one shared line has n ownership transfers (after the first); on separate lines it has 2 (one per core); bursts of k have n / k; a shared atomic counter equals the one-line case whatever the padding.
  - Cost recomputed from the transaction list; the cost curve is non-increasing in burst length (asserted).
- **Hostile input:** byte offsets are bounded sliders (0-127); two counters at the same offset are refused with "that is one counter, not two" (the layout is then the shared-counter case); run length is bounded. No typed text.
- **Honesty:** `Provenance kind="toy"` ("one cache line, atomic bus transactions, no store buffer, so real cores can show behaviour this model cannot") and `illustrative` on T = 100; `from-memory` on MESIF, MOESI, 128-byte lines and the padding APIs.

**Phone.** The four core rows stack (a `CellGrid` row is one line); the bus drawing is a `StageFrame minWidth={400}`; plots at 356. Buttons are in a 2 x 4 grid, 44px high.

**`timing-side-channels` · Timing & Side-Channel Attacks**

Batch rules above apply in full: every measurement on screen is **simulated**, the "secret" is a fixed fake from `fakeSecret`, and nothing here times anything real.
**Spec.**
- **Comparison counts (the real, deterministic part).** Two lesson-authored functions run on a fake token: an **early-exit compare** (returns at the first mismatching byte) and a **constant-time compare** (visits every byte and accumulates the differences with OR, then tests once). A reading of "the leak is only exploitable on a quiet LAN" is shown to be a statement about `n`, not about safety.

- **Secret-independent traces (the defender's test).** A tiny lesson-authored machine produces a **trace** of what an observer of a shared resource could see: the branches taken and the memory lines touched. Programs: a secret-dependent `if`, a table lookup indexed by a secret byte, a masked select (`(a & m) | (b & ~m)`), and the constant-time compare. The learner sets **two different secrets**; the lesson runs the program on both and compares the traces. **Verdict: leaks (traces differ) or does not leak in this model (traces identical).** This is the real methodology behind "constant-time" code (checking that control flow and memory access do not depend on secrets); tools that automate it exist (**verify** names such as `dudect` and `ctgrind`, from memory).

The scene is a **mitigation matrix** the learner toggles: serialising instructions, restricting speculation for indirect branches (retpolines), site and process isolation, flushing state on a domain switch, constant-time and bit-sliced cryptographic code, microcode updates. Each cell says what class of leak it addresses and what it costs. Chipped `from-memory`; **verify against** the Spectre paper (Kocher et al., 2018), the Meltdown paper (Lipp et al., 2018) and vendor guidance. No gadget code, no address pattern, no probing procedure appears.
- **What to use instead.** The names of library comparison functions, chipped `from-memory`: Node `crypto.timingSafeEqual` (it throws if the lengths differ), Python `hmac.compare_digest`, Go `crypto/subtle.ConstantTimeCompare`, Java `MessageDigest.isEqual`. **Verify each against** its documentation. Also: compare **HMACs** of both values so length is not leaked, and leave cryptography to vetted libraries.
**Out of scope.** Real timing measurements, network timing attacks in practice, power or electromagnetic channels, the Spectre mechanism in step-by-step form, constant-time proofs, compiler effects on constant-time code (one caption: compilers can undo it, which is why libraries use assembly or barriers).
**Kit.** `Plot2D` (`Bars` from `barsFromHistogram`, `Area`/`VLine` from K3-1 for the separation), `core/distributions` normal sampler (K3-1), `core/stats` `histogram`, `core/fakeSecret`, `core/random mulberry32`, `TextField` + a bounded text parser (UTF-8 bytes, 16 max), `ByteGrid` or `CellGrid` (the bytes compared, each cell lit as it is visited), `Segmented`, `Slider`, `Toggle` ×6 (the mitigation matrix), `.data-table` (matrix), `Stat` (K3-3: comparisons, samples needed), `Provenance` (`simulated`, seed shown, on every plot), `createRecorder`.

**`page-tables-tlb` · Page Tables & the TLB**
Track `os` · *"Translating addresses fast"* · Builds on: `virtual-memory-paging` · **[domain review]**
Fence quoted from `virtual-memory-paging`: *"The TLB, multi-level page tables and huge pages (T3 page-tables-tlb), mmap'd files and the page cache (T3), and fork's copy-on-write (T3 fork-copy-on-write)."* Tier 2 teaches a single-level table and faults; this lesson starts at "why one flat table is impossible".
**Spec.**
- **Walk scene (x86-64-style, four levels).** A 48-bit virtual address typed in hex (or picked from chips of mapped pages) and shown as a `BitStrip`: bits 47-39 PML4 index, 38-30 PDPT, 29-21 PD, 20-12 PT, 11-0 offset (9 + 9 + 9 + 9 + 12). Each table is 4 KiB holding 512 eight-byte entries.
  - A seeded toy memory holds about a dozen mappings spread across the address space. The walk draws four memory references (`table base + index x 8`), each reading an entry (present bit, next frame), ending at the frame number; physical address = frame x 4096 + offset. Counters: memory references, tables allocated.
  - **Sparse tables.** A stat compares the tables this process actually allocated with the flat table a 48-bit space would need: 2^36 entries x 8 bytes = 512 GiB. Computed, not typed.
  - Toggles: **huge page** (a 2 MiB mapping ends the walk at the PD level: three references, offset is 21 bits; a 1 GiB page ends at the PDPT, offset 30 bits), **unmap the page** (the walk stops at the first non-present entry and says at which level, a page fault), and a note that 5-level paging (LA57) adds one level (chipped `from-memory`).
  - **Canonical addresses.** Bits 63-48 must copy bit 47 on x86-64; an address that does not is refused by the walker with "not canonical" before any table is read (chipped `from-memory`; **verify against** the Intel SDM or AMD APM paging chapters).
- **TLB scene.** A small TLB (entries 4-64, default 8, a toy; real L1 data TLBs are around 64 entries and unified second levels around 1,500 or more, **verify against** a vendor manual or measured sources) with LRU replacement. The learner picks an access pattern: *sequential walk*, *stride*, *random over W pages* (working-set slider W in pages) and a page-size toggle (4 KiB or 2 MiB). A `CellGrid` with K3-16 `rowDecor` shows TLB entries (rail tone: valid, just used, just evicted).
  - Stats: hit rate, **average translation cost** = hits x 1 + misses x (references x a toy per-reference cost) and **TLB reach** = entries x page size (8 x 4 KiB = 32 KiB versus 8 x 2 MiB = 16 MiB). When the working set exceeds the reach the hit rate collapses (a cyclic scan over more pages than entries misses every time under LRU: the model shows it, and the caption is derived).
- **Context switches and shootdowns.** Two processes A and B alternate. With a TLB flush on every switch each process starts cold; with **address-space tags** (ASIDs, x86 PCID; chipped `from-memory`) entries survive. Then a multi-core scene: unmapping a page in a multi-threaded process must invalidate other cores' TLBs, so the initiating core interrupts the cores running that process (a **TLB shootdown**): IPIs = (cores running the process) - 1; a slider 1-16 cores and "batch m unmaps". Illustrative costs, labelled; one hedged line that mitigations for speculative-execution bugs made switches costlier (**verify**).
**Out of scope.** `mmap` and the page cache (`mmap-page-cache`, wave 5, built later: no link), copy-on-write (`fork-copy-on-write`, wave 5), IOMMUs, nested paging for virtual machines (one caption), page replacement policy (`virtual-memory-paging`), kernel memory layout.
**Kit.** `BitStrip` (the address, `groups` per level, `chunkGroups`), `core/bits` (BigInt arithmetic helpers or `parseBoundedBigInt` with `prefixes: ['hex']` for the address), `MemoryMap` or `ByteGrid` for the tables (a table's 512 entries are shown as a small window, `unit` 8), `RefArrow` for the walk, `CellGrid` + K3-16 (TLB entries), `Segmented` (page size, pattern), `Slider`, `Toggle`, `Stat` (K3-3), `Plot2D` (hit rate against working-set size, `VLine` at the reach), `createRecorder`, `core/format` (`bytes`), `Provenance`.
**AC.**
- **Watch (fields are a categorical split, stated in `watch`):** the four index fields use `orange`, `amber`, `pink`, `sky`, the offset is `violet` (it passes through untranslated); the entry being read is `--hi`; a present entry is `--ok`, a non-present entry or a canonical failure `--bad`; a TLB hit is `--ok`, a miss `--bad`; a just-evicted entry `--dim`.
- **Misconception:** "the page table is one big array in memory" and "the TLB caches data". Quiz: why does a four-level table not need 512 GiB? A second: a program cycles over 10 pages with an 8-entry LRU TLB; what is the hit rate?
- **Correctness (independent oracle: a flat `Map` and BigInt arithmetic).**
  - Index extraction equals `(va >> 39n) & 0x1ffn` and the other shifts for 10,000 seeded canonical addresses; the offset equals `va & 0xfffn`, `& 0x1fffffn` for 2 MiB pages and `& 0x3fffffffn` for 1 GiB pages.

  - Translation is a bijection on mapped pages: `translate(va) mod page size == va mod page size` and distinct pages map to distinct frames in the seeded layout.
  - Canonical check: a seeded set of 48-bit-sign-extension violations is refused; the same addresses sign-extended are accepted.
  - TLB: a cyclic scan over W pages with capacity C under LRU has hit rate 0 after warm-up when W > C and 100% when W <= C (asserted for C = 4-64); the reach equals entries x page size; the huge-page toggle never lowers the hit rate in the same stream (asserted).
  - Shootdown IPIs equal `cores running - 1` for a grid of core counts; a flush-on-switch run has at least as many misses as the ASID run on every seeded alternation.
- **Hostile input:** non-hex, over-long (more than 12 hex digits) and non-canonical addresses are refused with the message and the old address kept; an unmapped but canonical address is *valid input* and walks to a fault. `0x` and `_` are accepted via `parseBoundedBigInt`; `1e9` is refused.
- **Honesty:** `Provenance kind="toy"` ("x86-64-style, with the present and frame fields only; real entries carry permission, accessed and dirty bits") and `illustrative` on costs and TLB sizes; `from-memory` on LA57, PCID, canonical rules and the mitigation remark.

**`memory-allocators` · Memory Allocators & Fragmentation**
Track `os` · *"What malloc really does"* · Builds on: `stack-vs-heap`
Fence quoted from `garbage-collection`: *"allocators (T3 memory-allocators)"* and from `memory-safety-bugs`: *"allocator internals of any kind"* stayed out of Tier 2. This lesson owns allocation *policy* and fragmentation, and stays payload-free: **no heap metadata layout, no corruption, no grooming.** It shows free lists as a picture of holes, never as bytes an attacker could edit.
**Spec.**
- **Arena scene.** A heap bar of 64 units (16 bytes each, 1 KiB) drawn as blocks with `id` labels and free holes. The learner issues `alloc(n)` (n in units, 1-32) or clicks a block to `free` it, and picks a **policy**: *first fit*, *next fit* (resumes after the last allocation), *best fit* (smallest hole that fits), *worst fit* (largest hole). A **coalescing** toggle merges adjacent free blocks on free.
  - Live metrics: free total, **largest free block**, **external fragmentation = 1 - largest free / total free** (0 when nothing is free), blocks, holes. An allocation that fails although total free >= n is shown as `--bad` "fragmented: enough bytes, no hole big enough", never as "out of memory".
  - A **workload runner** replays a seeded script (200 operations: allocations of a size mix and frees of random live blocks) under each policy on the same script and shows a small table: failed allocations, final fragmentation, peak holes. Frees name objects, not addresses, so the script is valid under every policy.
- **Size classes scene.** Requests rounded up to a size class (slab and size-class allocators in jemalloc, tcmalloc and glibc work this way in spirit; the class table here is illustrative, **not** any real library's). A **class spacing** picker (12.5%, 25%, 50%, powers of two) and a seeded request-size histogram (log-uniform 8-2,048 bytes). Computed: **internal waste = sum(class - request) / sum(class)**, the worst-case waste for any single request, and the number of classes. Finer classes waste less and need more classes (and more partially filled slabs).
  - Caption: same-size slots are interchangeable, so a freed slot is always reusable by the next request of that class, which is why external fragmentation shrinks and internal waste appears instead.
- **Why memory stays high (RSS).** A long-lived heap of 256 pages (4 KiB), each holding k objects (k slider 1-16). The learner frees a fraction f of the objects with a pattern: *random*, *oldest first*, *contiguous from the end*. A page can go back to the operating system only if **every** object on it is free: the scene counts returnable pages against the freed bytes and draws pages as full, partly used, or empty (returnable). Random freeing of 90% of 8-object pages returns far fewer pages than 90%, which is the lesson. A garbage-collected heap can **move** survivors together (copying collection: `garbage-collection`), an allocator in C cannot because pointers are held elsewhere.
  - Allocator tuning knobs (`malloc_trim`, decay-based purging in jemalloc) are named in one chipped `from-memory` caption; **verify** names against each allocator's documentation.
**Out of scope.** Real allocator metadata layouts, security hardening, per-thread arenas and locks in depth (named), virtual memory and `mmap` (`page-tables-tlb` and `virtual-memory-paging`), garbage collectors (`garbage-collection`), Knuth's boundary-tag algorithms by name only.
**Kit.** `MemoryMap` (the arena: `regions` for blocks with `variant` `live` and `freed`, `unit` 1, a 64-row run or `unit` 4), or a lesson `Bar` with `segments` per block; `CellGrid` (the 256-page grid, `size="xs"`, canvas mode), `Segmented` (policy, spacing, pattern), `Toggle` (coalescing), `ChipButton` (alloc sizes, presets), `Slider`, `Stat` (K3-3), `Plot2D` (waste against class spacing, `Bars`), `core/random mulberry32`, `createRecorder`, `core/format` (`bytes`, `pct`), `Provenance`.
**AC.**
- **Watch:** a live block takes a plain category tone per block id (`amber`, `pink`, `sky`, `orange`), never `--ok`/`--bad`; a free hole is `--dim` outlined; the hole just used is `--hi`; a failed "fragmented" allocation and a page that cannot be returned are `--bad`; a returnable page is `--ok`; internal waste inside a class is `--violet` hatching.
- **Misconception:** "if free memory is at least what I asked for, malloc will succeed" and "free() gives memory back to the OS". Quiz: 40 units free in four holes of 10; can `alloc(16)` succeed? A second: you free 90% of the objects at random; why does the process's memory barely drop?
- **Correctness (independent oracle: brute force, and an analytic expectation).**
  - Invariants after every operation of 500 seeded scripts, for each policy and both coalescing settings: blocks tile the arena exactly with no overlap, free units + live units = 64, and with coalescing on no two adjacent holes exist.
  - **Policy choice:** best fit picks the smallest sufficient hole and worst fit the largest, first fit the lowest-address sufficient hole (each verified by a separate brute-force scan over the holes); next fit resumes from the previous allocation's end.
  - External fragmentation equals `1 - largest / total` recomputed from the hole list; the "fragmented" verdict fires exactly when `total free >= n` and `largest < n`.
  - Size classes: for every request size 17-4,096 the class is the smallest class >= the request; the worst-case waste over all sizes equals the enumerated maximum (asserted per spacing: about 33% for 50% spacing and just under 50% for powers of two); internal waste equals the recomputed sum.
  - Returnable pages: with random freeing of fraction f over p pages of k objects, the returnable fraction averages `f^k` (within 0.02 over 200 seeded runs); oldest-first freeing returns about f of the pages.
- **Hostile input:** `alloc` sizes are chip- or stepper-bounded 1-32; the script length is fixed; k and f are sliders. Freeing an already-free block is impossible from the UI and a model-level double free is refused with a sentence in the tests (never simulated as corruption).
- **Honesty:** `Provenance kind="toy"` ("a first-fit arena and a made-up size-class table; real allocators are far more elaborate, and nothing here models their metadata") and `from-memory` on the jemalloc, tcmalloc and glibc mentions and tuning functions.

**`regex-engines` · How Regex Engines Work**

**`parsing-algorithms` · Top-Down vs Bottom-Up Parsing (LL & LR)**
Track `lang` · *"Every compiler picks a side"* · Builds on: `parsing-ast`
Fences quoted: from `parsing-ast`, *"LL/LR tables and parser generators (T3 parsing-algorithms)"*; from `grammars-parsing`, *"LL vs LR and parser generators (T3 parsing-algorithms)."* The Tier 2 lessons build a parse tree by hand-written recursive descent and show a grammar; this lesson asks how a parser *decides* from tables.
**Spec.**
- **Grammar editor.** Rules like `E -> E + T | T`, one per line, nonterminals start with an uppercase letter, terminals are other tokens separated by spaces, `eps` for the empty string. At most 6 rules, 4 alternatives each, 5 symbols per alternative. Presets: **layered expressions** (`E -> E + T | T`, `T -> T * F | F`, `F -> ( E ) | id`), **LL-friendly expressions** (`E -> T E'`, `E' -> + T E' | eps`, ...), **ambiguous** (`E -> E + E | E * E | id`), **dangling else**.
- **Top-down (LL(1)) pane.** The lesson computes **FIRST and FOLLOW sets** and the **predictive table** (a `CellGrid`: rows nonterminals, columns terminals plus `$`). A cell with two rules is a **conflict**, outlined `--bad` with both rules shown. Left recursion is detected: with `E -> E + T | T` the table has a conflict and a recursive-descent parser would call itself without consuming input (the pane shows the call depth hit a **budget of 50** and stops: "recursion budget reached", not "infinite"). A button **"remove left recursion"** rewrites to the LL-friendly form and the conflicts go.
- **Bottom-up (SLR(1)) pane.** The lesson builds the LR(0) item sets (states list with the items; the automaton in `GraphView`), then the ACTION and GOTO tables using FOLLOW sets (SLR). A cell with both a shift and a reduce (or two reduces) is a conflict. For the ambiguous grammar the learner **resolves each shift/reduce conflict by choosing shift or reduce** in the cell (the toy equivalent of precedence declarations).
- **Lockstep run.** A token string (at most 12 tokens, presets such as `id + id * id`). Both parsers run on it one step at a time: top-down shows the **stack of expected symbols**, the input, and "expand E -> T E'" or "match id"; bottom-up shows the **state/symbol stack**, the input and "shift" or "reduce T -> T * F". Trees grow in opposite orders: top-down from the root (a leftmost derivation), bottom-up from the leaves (the reverse of a rightmost derivation); both orders are printed as derivations and compared with the tree.
- **Precedence game.** With the ambiguous grammar and the learner's two conflict choices (after `E + E` seeing `*`; after `E * E` seeing `+`), the tree for `id + id * id` is built and **evaluated with ids 2, 3, 4**: choosing "shift" then "reduce" gives 14, the other choices give 20 or other values. The lesson says which choices encode the usual precedence, and a wrong table is shown, not hidden.
- Real tools, chipped `from-memory`: hand-written recursive descent and Pratt parsing dominate in practice; yacc and Bison generate LALR(1); ANTLR generates adaptive LL; tree-sitter is LR-family with error recovery. **Verify** each before the sentence ships.
**Out of scope.** Full LR(1) and LALR(1) lookahead construction (SLR is used; the caption says LALR/LR(1) merge or split states to resolve more conflicts), error recovery strategies, Earley/GLR/PEG (named), grammar ambiguity proofs, building ASTs (`parsing-ast`).

**`chomsky-hierarchy` · The Chomsky Hierarchy & Pumping Lemma**
Track `lang` · *"Regular, context-free, and beyond"* · Builds on: `dfa-nfa`, `pushdown-automata` (earlier in this batch), `turing-machines` (wave 3) · **[domain review]**

**`metaprogramming-macros` · Metaprogramming, Reflection & Macros**
Track `lang` · *"Code that writes code"* · Builds on: `parsing-ast`
**Spec.**
- **Macro expander scene.** A toy expression language: numbers, variables, `+ - * /`, `let x = e in e`, a function `next()` that returns 1, 2, 3, ... on each call (a visible counter), and **macro definitions** `macro NAME(p, q) = template`. The learner edits the template (preset and free text, at most 60 characters, parsed by a hand-written parser) and the call's arguments, then picks an **expansion strategy**:
  - **Text substitution** (token-level, the C preprocessor model): `SQUARE(x) = x * x` called with `a + 1` expands to `a + 1 * a + 1`, which is `9` when `a = 4`, not `25`.
  - **Syntax-tree substitution** (the argument stays one subtree, as in Lisp or Rust macros): `(a + 1) * (a + 1)` is `25`. Calling it with `next()` evaluates the argument twice (`next() * next()` is `1 * 2`), which the counter shows. The fix is a template that binds the argument once: `let t = x in t * t`.
  - **Hygienic expansion:** the template's own binders are renamed so they cannot capture the caller's names. With the template `let tmp = 10 in x + tmp` called as `M(tmp)` where the caller's `tmp` is 2, non-hygienic expansion gives `tmp + tmp = 20`, hygienic gives `2 + 10 = 12` (`tmp#1` shown).
  - The expansion is shown as source on the left and the **expanded tree** on the right (`TreeSvg`), with the evaluation result and the counter beneath. A wrong result is shown, with the reason, never hidden.
  - A recursive macro that expands into itself hits an **expansion limit of 20** and says so.
- **Reflection scene (real JavaScript, fixed code).** A plain object `{ name: 'Ada', age: 36 }`. The learner reads properties through a real **`Proxy`** whose `get`, `has` and `ownKeys` traps log each interception; `Reflect.ownKeys` and `Object.keys` list the fields. A toy **serializer** is shown three ways, each producing JSON for the same object: **reflective** (walks the keys at run time), **generated** (a field list produced at build time), **hand-written**. The learner **adds a field** to the object's definition: the reflective serializer includes it, the generated one is **stale** until "regenerate" is pressed, the hand-written one needs a manual edit.
- **When does it run? scene.** Techniques: macro (expansion time), code generation (build time), decorator or annotation (definition time), reflection (run time), proxy (access time). A mistake picker (misspelled field, wrong type, field added later). The toy pipeline **runs** each technique's check at its phase and reports when the mistake surfaces: at expansion, at generation, at definition, at the first call, or never (a silently `undefined` property). The table is produced by the toy pipeline, not typed.
- Real systems, chipped `from-memory`: Lisp `defmacro` is not hygienic (programmers use `gensym`), Scheme's `syntax-rules` is, Rust's `macro_rules!` is hygienic for local variables, the C preprocessor is not; ORMs and DI containers use reflection or proxies; JavaScript decorators are a language feature in recent versions. **Verify each against** the language references.
**Out of scope.** Writing a full macro system, procedural macros' implementation, template engines, bytecode manipulation, `eval` (never used on learner text), compile-time evaluation in detail, debugging tools for generated code (one caption: generated code is what the debugger sees, so expansion must stay inspectable).

Fence quoted from `deserialization-path-traversal`: *"SSRF and broken access control stay in T3 ssrf-access-control."* This lesson **describes the class of bug and shows the fix**; it never lists addresses to try, never shows an encoding trick as a string, and never sends a request.
**Spec.**

**`envelope-encryption-kms` · Encryption at Rest & Envelope Encryption (KMS)**
Track `sec` · *"Keys to encrypt the keys"* · Builds on: `symmetric-ciphers` · **[domain review]**
Fence quoted from `symmetric-ciphers`: *"key wrapping and KMS stay in T3 envelope-encryption-kms; cipher internals (rounds, S-boxes) are named only."* The Tier 2 lesson teaches the cipher and the nonce rule; this lesson teaches **how keys are organised around it**.
**Spec.**
- **Hierarchy scene (real WebCrypto).** Three fictional tenants (Acme, Birch, Cedar) each with records the learner adds (text up to 64 characters, with a "never type a real secret" note; nothing is stored). A **simulated KMS service object** in the page holds one **key-encryption key (KEK)** per tenant as a **non-extractable** `CryptoKey` (a real WebCrypto property: the page cannot read the bytes). For each record the lesson:
  1. generates a fresh 256-bit **data key (DEK)**;
  2. encrypts the record with **AES-GCM** under the DEK with a random 96-bit IV and the record id as additional authenticated data;
  3. asks the KMS to **wrap** the DEK under the tenant's KEK (AES-GCM wrap with the tenant id as the **encryption context**, the real concept of binding a key to its context);
  4. stores `{ ciphertext, IV, wrapped DEK, KEK version, context }` and discards the plaintext DEK.
  - The picture is a three-level hierarchy (root key in hardware, KEK, DEKs, data) with the stored envelope laid out as `ByteGrid` fields. **Decrypt** runs the chain backwards through the KMS and shows each step.
- **Rotation scene.** *Rotate the tenant's KEK*: a new key version is made and every wrapped DEK is **re-wrapped** (unwrap under the old version inside the KMS, wrap under the new). The lesson shows the **data ciphertext bytes unchanged** (identical hash before and after) and counts bytes processed: re-wrapping touches about 60 bytes per record, **re-encrypting all data** touches every byte of it, with a records-and-sizes slider for how much data a tenant has. A separate button *rotate one record's DEK* re-encrypts that record (the only way to change the DEK itself). A caption names the real service behaviour of re-encrypting under a new key without exposing plaintext to the caller (AWS KMS `ReEncrypt` is the example, chipped `from-memory`; **verify**).
- **Shred and context scene.** *Destroy the tenant's KEK* (crypto-shredding): every wrapped DEK under it becomes unrecoverable, so every record of that tenant is unreadable **although the ciphertext still exists**, including in the backups the lesson shows. Real services impose a waiting period before deletion (chipped; **verify** the AWS and Google documentation) and the lesson says a shred only protects data that was always encrypted under that key. A second action: decrypt with the **wrong encryption context** (a record of Birch presented as Acme's): authentication fails (a real GCM failure, not a scripted one).
- **Why not the master key for everything?** A small comparison with a records-per-second slider: direct encryption calls the KMS for every record and has a payload limit (a few kilobytes in AWS KMS; **verify**), while envelope encryption calls it once per DEK unwrap (with a DEK cache, fewer), so KMS calls, latency and quota shrink. All counts come from the lesson's own runs, with illustrative per-call numbers labelled. A caption on random 96-bit nonces: NIST SP 800-38D limits how many messages one key may encrypt with random IVs (2^32), which is one reason for a **key per object** (chipped `from-memory`; **verify**).
**Out of scope.** The AES internals, key exchange and TLS (`diffie-hellman`, `tls-handshake`), HSM hardware and certification levels (named), password-based key derivation, key escrow and split knowledge, per-provider API details (named only).
**Kit.** `core/crypto` (`hasSubtle`, `toHex`, `sha256Hex`, `useAsyncValue`; the AES-GCM wrap and unwrap live in a lesson-local `envelope.ts` on `crypto.subtle`, since no other lesson needs them), `ByteGrid` (the envelope fields), `core/fakeSecret` (any credential-like sample text), `Segmented` (tenant), `TextField` (record text, bounded), `Slider`, `ChipButton`, `Stat` (K3-3: bytes processed, KMS calls), `Tray`, `Packet`/`Flyer` (key wrapping animation), `createRecorder`, `Provenance`, `useScenePicker`.
**AC.**
- **Watch:** key levels are `violet` for the root (structural), `info` for the KEK, `hi` for the DEK in use now, data bytes `muted`; a wrapped (protected) DEK is `--ok`; a destroyed KEK and the records it made unreadable `--bad`; the cheap path (re-wrap) is `--ok` and the costly one (re-encrypt everything) `--bad`; an authentication failure is `--bad` with the reason.
- **Misconception:** "rotating the master key re-encrypts all the data" and "deleting the key deletes the data". Quiz: after a KEK rotation, which bytes changed (the wrapped DEKs, not the data)? A second: after crypto-shredding a tenant, can its backup be read?
- **Correctness (independent oracle: `node:crypto` and an unchanged-bytes check).**
  - **Interoperability:** a record encrypted by the lesson's WebCrypto code decrypts with `node:crypto` `aes-256-gcm` given the (test-extractable) DEK, IV, AAD and tag, and the reverse direction too, for 200 seeded records; a published GCM test vector (McGrew and Viega's, or NIST's; **verify** the vector's source) passes through the lesson's encrypt function.
  - Rotation: after KEK rotation every record still decrypts; the **ciphertext and IV bytes are byte-identical** before and after (hash compared); every wrapped DEK differs; the old KEK version is no longer needed for new wraps.
  - Shredding: after destroying a KEK, decryption of every record of that tenant fails with the real `OperationError`, other tenants' records still decrypt, and the ciphertext bytes still exist and are unchanged (asserted).
  - Context: a wrap with context A fails to unwrap with context B; tampering with one byte of the ciphertext or the tag fails authentication for 200 seeded flips.
  - IV: 10,000 generated IVs under distinct keys are 12 bytes and no two collide in the seeded sample (a sanity check that says it cannot prove randomness).
  - Counts: re-wrap bytes = records x wrapped-DEK length, re-encrypt bytes = the sum of record sizes (recomputed), KMS calls for direct = records and for envelope = DEK unwraps (with and without a cache).

- **Honesty:** `Provenance kind="simulated"` on the KMS ("a service object in this page; a real KMS keeps keys in hardware and enforces access policy") and `real` on the cipher operations (WebCrypto); `illustrative` on call costs and sizes; `from-memory` on AWS, Google and Azure behaviours.

**`randomness-csprng` · Randomness & CSPRNGs**
Track `sec` · *"Math.random() is not a secret"* · Builds on: none (soft link in words to `birthday-paradox`, `hashing-encryption`) · **[domain review]** · payload-free
The attack idea is shown **only on the lesson's own toy generators**; the lesson never operates on `Math.random` output, a real token or anyone's session id.
**Spec.**
- **Lattice scene.** A **linear congruential generator** `x(n+1) = (a x(n) + c) mod m` with a preset picker (a toy with small `m` for a clear picture; a famous bad one; a "good-looking" one) and sliders for seed and count. A `Plot2D` of consecutive pairs `(x(n), x(n+1))` shows the points on **a small number of lines** (a lattice) for the toy; next to it, the same plot from **`crypto.getRandomValues`** is a uniform cloud.
  - **RANDU** (`a = 65539`, `m = 2^31`, a historically poor generator, **verify against** Marsaglia's 1968 note "Random numbers fall mainly in the planes"): the lesson shows triples `(x(n), x(n+1), x(n+2))` projected by a **rotation slider**; at the right angle the points collapse onto lines (planes seen edge on). The identity `x(n+2) = 6 x(n+1) - 9 x(n) mod 2^31` is computed and displayed, and the lesson counts the **15** distinct planes.
  - A caption states Marsaglia's bound (k-tuples lie on at most `(k! m)^(1/k)` hyperplanes), chipped `from-memory`.
- **State-recovery meter (toy only).** A toy generator of the lesson's own: a 16-bit LCG whose **output is the top 4 bits** of the state. The learner reads outputs one at a time; the lesson shows a meter of **how many of the 65,536 possible states are still consistent with what has been seen**: about 4,096 after one output, 256 after two, 16 after three, and usually 1 after four (computed by a brute-force pass over all states, not typed). When one remains, the lesson shows that **every later output is now known**, and compares its predictions with the real next outputs. The point: *a generator whose state can be inferred from its outputs is not secret, however random it looks*. The stage says the solver is a brute force over this toy's 65,536 states and is not a method for anything real. **No step is offered for any real generator.**
  - **Seed entropy.** A slider for how coarsely a seed is chosen: a clock read in whole seconds, in milliseconds, or a random 128-bit value from the system. The lesson shows **the number of seeds an observer who knows roughly when it was made would have to consider** (for a day: 86,400, about 16.4 bits; in milliseconds: about 26.4 bits; 128 bits: far beyond reach), in bits via `log2`.
- **Choose the right source (a classification game).** Eight uses to sort into **needs a CSPRNG**, **a reproducible seeded PRNG is what you want**, **any PRNG is fine**: a session identifier, a password-reset token, an AES-CBC IV, an API key, a Monte Carlo run you need to reproduce, a procedural level generated from a seed, retry backoff jitter, shuffling test data. A reveal states the reason for each. A separate caption covers nonces: for AES-GCM the requirement is **uniqueness per key**, not secrecy, so a counter works as well as random bytes (within the limits). Sources named, chipped `from-memory`: `crypto.getRandomValues` and `crypto.randomUUID` in browsers (a version 4 UUID carries 122 random bits), `crypto.randomBytes` in Node, the operating system's generator (`getrandom`, `/dev/urandom`, `BCryptGenRandom`); `Math.random` is not specified to be secure (V8 uses xorshift128+, **verify**). **Verify each against** MDN and the platform documentation.
- **Modulo bias.** Drawing a number 0-5 with `byte % 6`: the lesson enumerates **all 256 byte values** and shows the exact counts, 43 hits each for 0-3 and 42 each for 4-5 (because 256 = 42 x 6 + 4), then the fix: **rejection sampling** (discard bytes at or above 252 and draw again) giving 42 each. A slider for the range (2-20) shows the bias for other n.
**Out of scope.** Designing or analysing a CSPRNG (Fortuna, ChaCha-based generators, hardware entropy sources: named), randomness tests batteries beyond one sanity check, key generation for specific algorithms, password hashing (`hashing-encryption`), hash-based nonces.
