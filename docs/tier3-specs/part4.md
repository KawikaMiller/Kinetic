**`dma-io-devices` · I/O Devices, DMA & Memory-Mapped I/O**
Track `hw` · *"How hardware talks to the CPU"* · Builds on: `interrupts-context-switch` · **[domain review]**
**Spec.** Starts where `interrupts-context-switch` stops: it taught how an interrupt reaches a handler; this lesson asks how the *data* gets from a device to RAM and how the CPU names a device at all.
- **Scene 1, three ways to move a block.** A bus drawn with CPU, RAM and one device (a disk or NIC, a `Segmented` picker). The learner sets the transfer size (64 B to 64 KiB, `Slider`, log steps) and picks the mode: **programmed I/O** (the CPU reads a device data register word by word), **interrupt-driven PIO** (the CPU is told when the device has a word or buffer ready, then still copies it), **DMA** (the CPU writes a source, destination and length into the device's registers and goes back to work; the device masters the bus and raises one interrupt at the end). A `GanttLanes` has lanes CPU, bus, device. CPU bars are `work` (copying) or `wait`-free "useful job" bars; the DMA setup and the completion interrupt are K3-11 instants.
- A fixed 1,000-tick **useful job** runs on the CPU. The stat row shows ticks the CPU spent copying, ticks it got for the job, bytes delivered, and bus ticks lost to contention. Model: PIO costs `words × PIO_WORD_TICKS` of CPU, DMA costs `DMA_SETUP_TICKS + IRQ_TICKS` of CPU and `words × BUS_WORD_TICKS` of bus time; while the device holds the bus (burst mode) a CPU memory access stalls (cycle stealing is the other option, a `Toggle`). Constants are named and shown in a legend, labelled illustrative.
- **Scene 2, a device is an address.** A physical address map as a `CellGrid` strip (RAM, a ROM, a device register window). The learner reads or writes an address and sees where the access is routed: RAM stores the value, the register window calls the device. The toy device has three registers: `STATUS` (reading it **clears** the "ready" flag: a side effect), `DATA`, `CONTROL`. Reading `STATUS` twice gives different answers, the point of `volatile`. A `Segmented` toggle contrasts port-mapped I/O (a separate address space, x86 `in`/`out`) with memory-mapped I/O (ordinary loads and stores). A cached/uncached toggle shows why device windows are mapped uncached: a cached `STATUS` read returns the stale line forever (the model really caches the first read).
- **Scene 3, the descriptor ring.** A NIC-style ring of 8 descriptors (`CellGrid` ring, row tone per state: free, owned by device, filled, being processed). The driver posts empty buffers, the device DMAs a packet into the next owned descriptor, sets DONE, and interrupts. The learner sets the arrival rate and an **interrupt coalescing** threshold (raise one interrupt per N packets or after T ticks). Stats: interrupts raised, packets per interrupt, worst latency from arrival to driver seeing it. The learner can also make the driver slow, so the ring fills and the device drops packets (counted, not hidden).
- **Scene 4 (small panel), DMA and the cache.** Two toggles, "device DMA is cache-coherent" and "IOMMU on". With coherence off and no invalidate, the CPU reads a stale cached copy after DMA wrote RAM (the model has a real cache line). With the IOMMU off, a DMA to a wrong address overwrites an unrelated buffer; with it on, the access is blocked and logged. Captions say which platforms behave which way is hedged ("many x86 systems keep DMA coherent with CPU caches; many ARM designs need explicit cache maintenance: verify against the platform manual").
**Out of scope.** Interrupt delivery, masking and the context switch (`interrupts-context-switch`); zero-copy `sendfile`, kernel bypass and `io_uring` are named only (`io-models` owns `io_uring`); PCIe link layers, scatter-gather lists beyond one sentence; the page cache (`mmap-page-cache`).
**Kit.** `GanttLanes` (lanes, `kind: 'wait' | 'blocked'`, K3-11 instants for the setup write and the completion IRQ), `CellGrid` (address map and ring; K3-16 `rowDecor` for descriptor states), `Slider` (size, rate, with `format`), `Segmented`, `Toggle`, `Stat`, `useScenePicker`, `core/format` (`humanDuration`), `useTickSim` (K3-2) for the ring, `Provenance` (K3-7).
**AC.**
- Watch: CPU copying `--hi`; useful CPU job `--ok`; the bus held by the device `--info`; stalled CPU access `--orange` (a category, not an error); a dropped packet or stale read `--bad`; descriptor states take row tones (free `--dim`, device-owned `--info`, filled `--hi`, processed `--ok`); register window `--violet`.
- Misconception: "with DMA the CPU is not involved" and "DMA is free". The CPU still programs the transfer and takes the interrupt, and the bus is shared. A quiz question gives a 64 KiB transfer where PIO needs 8,192 words of CPU and asks which cost DMA removes.
- Correctness: CPU copy ticks equal `words × PIO_WORD_TICKS` exactly for PIO and equal `DMA_SETUP_TICKS + IRQ_TICKS` for DMA at every size on the slider (closed form, asserted at all steps). Conservation: bytes delivered equal bytes requested in every mode; the ring never has a descriptor both device-owned and processed, head and tail indices stay in `[0, 8)` and `produced - consumed <= 8` over 200 seeded arrival schedules. **Broken variant** the test must reject: a driver that re-posts a descriptor before DONE, which overwrites an unconsumed packet; the test says on which seed. Coalescing: interrupts raised equals `ceil(packets / N)` when the time threshold never fires (closed form), and never exceeds the packet count.
- Hostile input: sizes, rates and thresholds come from sliders and `parseBoundedInt`; an address typed in scene 2 is hex, refused with a message if non-hex, odd length or outside the 32-bit toy map, old value kept.
- Honesty: Provenance chips "illustrative ticks, not measured" and "toy device, registers invented"; the stale-cache and IOMMU panel says "which hardware behaves like this: verify against the platform manual".
**Phone.** Gantt lanes in `WideRegion minWidth={520}` with the stats above; the address map is a vertical strip at 390; the ring is 8 cells and fits. Scene picker wraps.

**`io-models` · Blocking, Non-Blocking & Async I/O**
Track `os` · *"select, epoll, io_uring"* · Builds on: `event-loop` · **[domain review]**
**Spec.** `event-loop` showed one thread juggling callbacks; this lesson shows what the kernel offers underneath it and what each model costs per connection.
- **Scene 1, one server, five models.** A server handles C connections, of which a fraction `a` are active in each round. `Segmented`: **blocking, thread per connection**; **non-blocking busy poll** (call `read`, get `EAGAIN`, loop); **`select`/`poll`** (hand the whole fd set in, scan it all on return); **`epoll`** (register once, the kernel returns only the ready ones); **completion-based (`io_uring`-style)** (submit operations, collect completions). Sliders: connections C (10 to 10,000), active fraction `a` (1% to 100%), a per-request work time. A seeded arrival process (K3-2 `createTickSim`) drives every model with the *same* events.
- Per model the sim counts, never estimates: **syscalls issued**, **fd entries examined by the kernel**, **wasted wake-ups**, **threads and their stacks** (stack size is a named constant, default 8 MiB *virtual* per the usual Linux default, with a note that it is address space, mostly not resident: verify against `ulimit -s` and `man pthread_create`), and requests served per round. `Stat` rows with K3-3 multi-line subs.
- `GanttLanes` with thread lanes: blocked threads are `kind: 'blocked'` (dashed), a worker on a ready fd is work, an idle loop thread is `wait`. For 3 connections the lanes show a thread-per-connection pool stalled in `read` while one `epoll` loop fans events out.
- **Scene 2, an `strace` of an echo server.** A `LogStream` (K3-9) prints the call sequence the simulator issued for 3 connections and 6 events under the chosen model (`epoll_wait` returns two ready fds, `read`, `write`, ...). Provenance: "simulated trace in strace style". The learner steps it and clicks a line to see the matching row in the lanes.
- **Scene 3, level vs edge triggering.** One connection receives 300 bytes; the handler reads a learner-chosen number of bytes (`Slider`, 50 to 300). Level-triggered `epoll` reports the fd again while data remains; edge-triggered reports it once per arrival, so a handler that stops early never hears about the rest until more data arrives, and the connection looks hung. A "read until `EAGAIN`" toggle fixes it. The stall is produced by the model, not scripted.
- **Scene 4, readiness vs completion, and files.** A `Segmented` of "socket" and "regular file". `epoll` reports a socket when a read would not block; a regular file is reported as always ready or cannot be registered at all (the caption says what Linux does, hedged: "`epoll_ctl` refuses regular files with `EPERM`, verify against `man 7 epoll`"), which is why disk I/O needs a thread pool or a completion interface. Completion-based I/O is shown as submit and collect queues (two rings), with the in-flight count.
**Out of scope.** The JavaScript microtask and macrotask order (`event-loop`); `async/await` sugar (`async-await-coroutines`); `epoll` internals (red-black tree, wait queues) are one sentence; Windows IOCP and kqueue are named only; DMA (`dma-io-devices`).
**Kit.** `useTickSim` (K3-2), `GanttLanes` (`barAt` K3-10 for the progressive reveal, K3-11 instants for syscalls), `LogStream` (K3-9, `highlight`, `live: 'off'`), `Slider`, `Segmented`, `Toggle`, `Stat` (K3-3), `timeFrames` (K3-14) for the scene 3 stepper, `Provenance`.
**AC.**
- Watch: a blocked thread is `--dim` dashed with a stack bar in `--violet`; an active worker `--hi`; a ready fd `--ok`; a wasted wake-up or `EAGAIN` `--orange`; a hung (never-notified) connection `--bad`; the kernel's scan `--info`.
- Misconception: "epoll is faster because it is asynchronous" and "non-blocking I/O means no waiting". The cost difference is that `select`/`poll` scan all C fds each call while `epoll` returns only the k ready ones, and busy polling burns calls on `EAGAIN`. Quiz: with 10,000 idle connections and 5 ready, how many fd entries does each call examine.
- Correctness: every model serves exactly the same set of events (each event handled once, none lost) over 200 seeded schedules. Closed forms asserted against the counters: `select`/`poll` examine `C` entries per call; `epoll_wait` returns `k` entries, where `k` is the number ready; thread-per-connection uses `C` threads and `C × stackBytes` of virtual stack. An independent brute-force reference scans the event list and counts ready fds per round; the sim equals it. **Broken variant:** edge-triggered with a partial read leaves bytes unread and the test asserts the stall is reported ("hung", never "idle"); the same schedule with drain-to-`EAGAIN` completes.
- Hostile input: C and `a` are slider-bound; a typed read size is a bounded integer; a 0-byte read is refused as "read of 0 is a no-op, pick 1 or more".
- Honesty: "simulated server and arrivals (seed N); real servers add parsing, TLS and scheduling"; stack size and `EPERM` carry "from memory, verify against the man page"; Provenance chips on the trace and the cost constants.
**Phone.** Lanes in `WideRegion minWidth={560}`; the `LogStream` wraps; counter stats stack in two columns. Scene 3's byte strip is a `BitStrip`-style `ArrayStrip` with `size="sm"`.

**`fork-copy-on-write` · fork, exec & Copy-on-Write**
Track `os` · *"Cloning a process for free"* · Builds on: `virtual-memory-paging` · **[domain review]**
**Spec.** `virtual-memory-paging` taught one address space mapped by one page table and left sharing frames out of scope; this lesson shares frames.
- **Scene 1, fork.** A parent process with 8 pages (`CellGrid`, a page table row per process, a frame pool row beneath). `fork()` creates a child whose page table entries point at the **same frames**, all marked read-only with a COW flag, and each frame's reference count rises to 2. Nothing is copied. Stats: frames in use, bytes copied (0), `fork` cost in table entries copied (8, not 8 pages of data).
- **Scene 2, write.** The learner clicks a page in either process to write it. A write to a shared read-only page raises a page fault; the handler allocates a new frame, copies 4 KiB, remaps the writer's entry writable, and drops the old frame's count. If the count is already 1 (the other process has since copied or exited) the page is simply made writable, no copy: the "last one standing" case. A **Fault log** lists each fault and what the kernel did. The learner sees the two processes read different bytes after the write; neither sees the other's write.
- **Scene 3, three real uses** (presets): **Redis-style snapshot** (a child walks a data set to write it to disk while the parent keeps taking writes; a slider sets the parent's write rate, and memory grows by the number of *distinct pages* the parent dirtied while the child lived: the model counts it); **pre-fork server** (workers share the loaded code and read-only data, and a worker's private writes copy only those pages); **fork then exec** (`exec` replaces the mappings, so almost nothing was ever copied, which is why the shell's fork-then-exec is cheap, and why `posix_spawn`/`vfork` exist, named only). A "huge pages" toggle makes the copy unit 2 MiB instead of 4 KiB with a caption that one write now copies 512x as much (hedged: "transparent huge pages behaviour varies, verify against the kernel docs").
- A second tab, **What fork does not share**, is a small table: file descriptors are duplicated and share the open file offset; only the calling thread exists in the child; `fork` returns the child's pid in the parent and 0 in the child. The learner presses fork and reads both return values off the two process cards.
**Out of scope.** Page-table structure, multi-level tables and the TLB flush on fork (`page-tables-tlb`, wave 7: named, not linked); process scheduling; containers' process trees (`containers`); `clone` flags are named only.
**Kit.** `CellGrid` (K3-16 `rowDecor` for the two process rows and the shared-frame rail), `MemoryMap` is not needed, `Segmented`, `Slider`, `Stat`, `ChipButton` presets, `createRecorder` for scene 1-2 frames, `LogStream` (K3-9) for the fault log, `Provenance`.
**AC.**
- Watch: a frame shared by two page tables is `--violet` with its count; a page-table entry that is read-only+COW is outlined `--info`; a write fault is a `--hi` pulse on the entry; a frame that was copied is `--ok` (new, private); a frame freed (count 0) is `--dim`. Memory growth in the snapshot preset is `--bad` only for the part above the pre-fork baseline, because that is the costly side of the comparison.
- Misconception: "fork copies all the memory" and "a write in the child changes the parent". A quiz question gives a 1 GiB parent that forks and the child writes 8 pages, and asks how much is copied.
- Correctness: independent oracle is a **naive fork** that deep-copies the whole address space. For 200 seeded sequences of reads, writes and forks (up to 3 processes) the bytes every process reads equal the naive model's, byte for byte. Invariants asserted after every step: each frame's reference count equals the number of page-table entries mapping it; a frame with count > 1 is never mapped writable; no frame leaks after all processes exit (the pool returns to full). Expected distinct pages dirtied by `w` uniform writes over `N` pages is `N × (1 − (1 − 1/N)^w)`; the snapshot preset's copied-page count over 2,000 seeded runs matches it within a stated tolerance. **Broken variant:** a handler that writes through a shared page without copying makes the child's write visible in the parent; the test asserts the divergence from the naive oracle.
- Hostile input: page index and byte value come from clicks and a bounded hex field; an out-of-range page is not offered; write rate and process count are bounded sliders.
- Honesty: "a toy MMU with 8 pages of 4 KiB; real kernels also track dirty and accessed bits, swap and file-backed pages"; the Redis, pre-fork and huge-page statements are chipped from memory ("verify against Redis docs and `man 2 fork`").
**Phone.** Two process rows at 8 cells each fit 390 at `size="sm"`; the fault log sits below; the preset chips wrap.

**`mmap-page-cache` · mmap & the Page Cache**
Track `os` · *"Why the second read is fast"* · Builds on: `virtual-memory-paging`, `buffer-pool`, `file-systems` · **[domain review]**
**Spec.** Opens by quoting `buffer-pool`'s line: that lesson owned a *database-managed* pool (pin counts, dirty pages, clock sweep, scan resistance). This lesson owns the **operating system's** cache of file pages, shared by every process, and the two ways to reach it. `file-systems` already says `write()` only reaches the page cache and needs `fsync`; this lesson shows *why* with the cache drawn.
- **Scene 1, read() vs mmap.** A file of 64 pages on disk (`CellGrid`, row tone: not cached, cached clean, cached dirty), a page cache with a capacity slider (8 to 64 pages), and two process views. A `Segmented` picks the access method: **`read()` into a buffer** copies each requested page from the cache into a user buffer (one copy, counted); **`mmap`** maps cache pages into the process address space, so access is a load with no copy; the first touch of an unmapped page raises a **fault**: a **minor fault** if the page is already in the cache (map it, no disk), a **major fault** if it must be read from disk first. Stats: disk reads, minor faults, major faults, bytes copied to user space, cache hit ratio.
- The learner chooses the access pattern (sequential, random, repeat the same 8 pages, two processes reading the same file) and presses Play. Two processes reading one file share the same cached pages (the second sees only hits).
- **Scene 2, readahead.** Under sequential access the model detects the pattern and doubles the prefetch window on each hit up to a cap (a named constant, in the spirit of Linux's default `read_ahead_kb`, verify against the kernel docs), so later reads are hits before they are asked for; random access resets it. A plot (`Plot2D`) of hit ratio against window size is **computed** by running the same trace through the model at each window.
- **Scene 3, dirty pages and the power cut.** The learner writes to pages via `write()` or via the mapping (the page turns dirty). Dirty pages are flushed to disk by a background writeback timer, or at once by `fsync`/`msync`. Three buttons: **kill the process** (the dirty pages stay in the cache; the kernel still writes them back, so nothing is lost), **power cut** (everything in RAM is gone: only pages already flushed survive), **fsync then power cut**. A `Toggle` "acknowledge the write before or after `fsync`" feeds the scene's verdict: "the application told the user it was saved" versus what survives.
- A small memory-accounting note: file-backed pages count towards a process's resident set while mapped, and the same page is counted for several processes ("shared"); in a cgroup the page cache is charged to the cgroup that touched it (hedged: verify against the cgroup docs). Pitfalls row: a truncated file turns a mapped access into `SIGBUS`; an I/O error on a mapped page also surfaces as a signal rather than a return code.
**Out of scope.** Database pin counts, clock sweep, scan resistance (`buffer-pool`); journalling and inodes (`file-systems`); the page-table structure and TLB (`page-tables-tlb`, named); `O_DIRECT` and `io_uring` are named only.
**Kit.** `CellGrid` (K3-16 row tone, per-page state; `onCellClick` to touch a page), `Plot2D` (`Curve`, `VLine`), `Segmented`, `Slider`, `Toggle`, `Stat`, `ChipButton` presets, `createRecorder`, `core/random` (`mulberry32`) for traces, `Provenance`.
**AC.**
- Watch: a page not cached is `--dim`; cached clean `--ok`; cached dirty `--hi`; a major fault (disk read) `--bad`; a minor fault `--info`; a user-space copy `--orange`; the shared mapping into two processes `--violet`; flushed-to-disk is an `--ok` tick.
- Misconception: "mmap loads the whole file into memory", "the second read is fast because of the CPU cache", and "write() returned, so it is on disk". Quiz: kill -9 the writer after `write()` but before `fsync`, then pull the power: which bytes exist.
- Correctness: hits, minor and major faults come from a page-cache model (LRU eviction, readahead, dirty tracking), checked against an independent reference that replays the access list with a plain LRU list and no readahead; hit ratio equals the reference when the window is 1. Identities asserted: `read()` copies exactly the bytes requested; `mmap` copies 0 bytes to user space; `minor + major` equals the number of distinct pages first touched per process. **Durability invariant over 200 seeded write/crash schedules:** after a power cut, a page holds the last value that was flushed or fsynced before the cut, never a later unflushed one; with "ack after fsync" no acknowledged write is ever lost. **Broken variant:** "ack before fsync" loses an acknowledged write on at least one seed, which the test names and the stage displays (seed shown).
- Hostile input: file size and cache capacity are bounded sliders; a typed page number in scene 1 is `parseBoundedInt` (refuses non-integers and out-of-range with the reason).
- Honesty: "an LRU toy with a 64-page file; Linux uses more elaborate lists, per-device writeback and read-ahead heuristics"; fault names, `SIGBUS`, cgroup accounting and the readahead default carry "from memory, verify against `man 2 mmap` and the kernel docs"; Provenance "simulated, seed N".
**Phone.** The 64-page file strip uses `CellGrid size="xs"` in a `WideRegion minWidth={420}`; the two process views stack; the plot is 356 wide.

**`write-ahead-log` · Write-Ahead Logging & Crash Recovery**
Track `data` · *"Log first, then write"* · Builds on: `transactions-acid` · **[domain review]**
**Spec.** Opens by quoting `transactions-acid`'s line (it showed that the change is logged before the data is touched and that restart redoes committed work and undoes the rest, as a story with one crash). This lesson is the mechanism: **log sequence numbers, the steal/no-force policy, page LSNs, checkpoints, redo then undo, and the fsync boundary**, with the crash placed by the learner anywhere. `file-systems` journaling is the same idea for metadata; named, not repeated.
- **Scene 1, the machine.** A toy database of 8 integer pages, a buffer pool in memory (pages may be dirty), a data file on disk, and a **log** with a volatile tail (in memory) and a durable part (fsynced). Each log record has an LSN, a transaction id, and one of `update (page, before, after)`, `commit`, `abort`, `checkpoint`, `undo` (a compensation record). Each page has a **page LSN**: the LSN of the last record applied to it. The learner runs transactions from a `Segmented` list of presets or by clicking "T1 writes page 3 = 7" buttons, and controls the buffer pool: **flush a page** now, **fsync the log** now, **checkpoint**, **commit**, **abort**.
- **Policy toggles.** `Steal` (a dirty page of an *uncommitted* transaction may be flushed before commit: needs undo) and `Force` (all of a transaction's pages must be flushed at commit: avoids redo, but a commit then costs random page writes). The lesson's default is steal / no-force, and the cost panel shows why: commit cost is one sequential log append plus one fsync, not N random page writes.
- **The WAL rule, enforced.** A page may be flushed only if the log is durable up to its page LSN. A `Toggle` "enforce the WAL rule" switches this off (the broken mode below). A commit may be acknowledged only after the log is durable up to the commit record; a second `Toggle` "acknowledge before fsync" breaks it.
- **Scene 2, crash anywhere, then recover.** A **Crash now** button at any step (including between a log record being written and fsynced, and a torn last record: a checksum failure on the log tail, so the final partial record is ignored). Recovery runs step by step with a `CodePanel` of the algorithm: **redo** from the checkpoint's redo point, applying an update only if `page.lsn < record.lsn` (so redo is **idempotent**), then **undo** the transactions with no commit record, in reverse LSN order, writing `undo` records. A **Crash during recovery** button repeats the crash mid-redo or mid-undo, then recovers again: the page LSN and the `undo` records make the second recovery correct.
- **Scene 3, group commit.** `fsync` latency slider (named constants: roughly 0.1 to 1 ms for an SSD and about 10 ms for a spinning disk, illustrative, verify against your device) and a number of concurrent committers. Without grouping a commit needs its own fsync: throughput is at most `1 / latency`. With group commit, `g` committers waiting at the same moment share one fsync: throughput about `g / latency`. A `Plot2D` of commits per second is computed from a seeded arrival process.
- **Checkpoints** shorten recovery: the redo-start LSN is shown on the log strip; a slider for the checkpoint interval trades recovery time (records to replay) against write overhead. The learner reads off "records replayed" after recovery.
**Out of scope.** Isolation, locks and MVCC (`isolation-levels`, `mvcc`); the full ARIES analysis pass and fuzzy checkpoints are named, the lesson uses a simplified sharp checkpoint and says so; file-system journals (`file-systems`); replication of the log (`replication`); the CDC reader of the log (`change-data-capture`).
**Kit.** `LogStream` (K3-9) for the log records (rows keyed by LSN, `highlight` on the record being redone), `CellGrid` (K3-16 `rowDecor`: pages with a rail for dirty / durable / page LSN), `CodePanel` (recovery algorithm, `stateOf` per line), `Plot2D`, `createRecorder` for the recovery frames, `Toggle`, `Segmented`, `Slider`, `Stat`, `core/random`, `Provenance`.
**AC.**
- Watch: committed transaction's records `--ok`; uncommitted (a loser) `--bad` while it is a loser, `--dim` once undone; the durable boundary of the log is a `--violet` rule; the volatile tail `--dim` dashed; a page whose LSN is behind the log `--hi` (redo needed); a page flushed is an `--info` tick; a torn record is `--orange` with "ignored".
- Misconception: "commit means the data pages are on disk", and "the log is only for undo". Quiz: after a crash, a committed transaction's page was never flushed: which pass fixes it, and why does a loser's flushed page need the log's before-image.
- Correctness: oracle is a **serial replay**: apply the operations of exactly the transactions that committed, in commit order, to an empty database. **Invariants checked after recovery, at every injected crash point over 200+ seeded schedules** (random flushes, fsyncs, checkpoints, a crash at a random step, an optional second crash during recovery): **D** every transaction acknowledged as committed has all its writes present; **A** no uncommitted transaction's write is present; recovered state equals the serial replay. Recovery run twice gives the same state (idempotence). **Broken modes, each must violate on some seed:** (1) "WAL rule off": a page of an uncommitted transaction reaches disk with no durable log record, so undo has nothing to restore and **A** fails (hand-built: T1 writes page 3, the page is flushed, crash before the log fsync); (2) "acknowledge before fsync": **D** fails (hand-built: T1 commits, the ack shows, crash before the fsync). The lesson shows the counterexample seed and the shortened trace.
- Hostile input: page numbers and values are bounded integers via `parseBoundedInt`; a 33rd transaction is refused with "the toy log holds 64 records, checkpoint or reset"; sliders are bounded.
- Honesty: Provenance "simulated, seed N", "simplified ARIES: sharp checkpoint, no analysis pass, one log"; the SSD and HDD fsync figures are "illustrative, verify against your device"; "Postgres calls its log the WAL, InnoDB has a redo log, SQLite has a WAL mode: names differ, check your database" (from memory).
**Phone.** The log strip is a `LogStream` that wraps; the page grid fits 8 cells; the recovery `CodePanel` lines are short (K3-6 fix applies); controls in `flex-wrap` rows.

**`merkle-trees` · Merkle Trees & Anti-Entropy**
Track `data` · *"Verify one leaf without downloading the forest"* · Builds on: `git-internals` · **[domain review]**
**Spec.** Opens by quoting `git-internals`: it taught content-addressed objects and trees as a storage model. This lesson uses hash trees to **compare** and **prove**: anti-entropy, inclusion proofs, repair. Real SHA-256 (`crypto.subtle`) throughout, displayed truncated to 4 hex characters with the truncation labelled (display only; the full hash is what is compared).
- **Scene 1, build one.** 8 or 16 leaves (editable text blocks, `TextField`). Leaf hash `SHA-256(0x00 || data)`, parent hash `SHA-256(0x01 || left || right)`, the domain-separated form used by Certificate Transparency (RFC 6962 §2.1: verify against the RFC before quoting the section). Editing a leaf turns its **ancestor path** `--bad` up to the root; siblings stay `--ok`. An **odd leaf count** `Segmented`: *split at the largest power of two below n* (RFC 6962) versus *duplicate the last node* (a Bitcoin-style rule, from memory: verify). With duplication, the trees for `[a, b, c]` and `[a, b, c, c]` have the **same root**, shown side by side; the lesson says why a leaf-count or domain separation matters.
- **Scene 2, anti-entropy between two replicas.** Replica A and B each hold 16 key ranges as leaves. The learner changes `k` leaves on one side (a `Slider` 0 to 6, or clicking leaves). Press Sync: compare roots (equal means done), otherwise **descend only into children whose hashes differ**; every hash comparison is counted and drawn. Result: the exact set of differing leaves is found, transferred, and the trees match. Compared with the naive "send everything" (16 leaf comparisons). Stats: hash comparisons, leaves transferred, bytes saved. A third panel varies `n` (16 to 4,096, computed only) to show comparisons growing as about `k × log2(n)`, not `n`.
- **Scene 3, inclusion proof.** Pick any leaf; the proof is the **sibling hashes along its path** (`ceil(log2 n)` of them). A verifier box recomputes the root from the leaf plus the proof and compares it with the trusted root. The learner tampers with the leaf, a sibling or the claimed index and the verdict turns `--bad`. Proof size versus data size is plotted.
- **Scene 4, a toy that fails.** A `Toggle` "toy 8-bit hash" truncates every node hash to 8 bits (labelled toy). Anti-entropy then **misses a difference** when two different subtrees collide on 8 bits, found by the model on a seeded set of edits. This shows why hash width and not "hashes are unique" is what makes the comparison trustworthy.
**Out of scope.** Git objects and commits (`git-internals`); hash functions' internals (`hashing-encryption`); signatures and certificate chains; replica membership and gossip (named); this is integrity, not secrecy and not a security design.
**Kit.** `TreeSvg` (`shape` of a complete binary tree, node marks), `crypto.ts` (`sha256Hex`, `useAsyncValue`), K3-8 `createCluster` (two replicas and the compare messages), `SequenceDiagram` (compare rounds), `TextField`, `Segmented`, `Toggle`, `Slider`, `Plot2D`, `Stat`, `core/random`, `Provenance`.
**AC.**
- Watch: a hash that matches its twin `--ok`; one that differs `--bad`; the path of recomputed hashes `--hi`; a subtree skipped without descent `--dim`; the proof's sibling hashes `--violet`; a toy-collision node `--orange`.
- Misconception: "a Merkle tree stores the data" and "you must download everything to verify one block". Quiz: 1,024 blocks and one differs between replicas: roughly how many hash comparisons does anti-entropy need, against the naive count.
- Correctness: the leaf and node hashes equal an independent `node:crypto` SHA-256 over the same bytes for every node over 200 seeded trees; the root of an RFC 6962 tree equals a published CT test vector for the empty tree (`SHA-256("")`) and small trees (verify the vectors against the RFC or a reputable implementation, hand-checked once). Anti-entropy returns **exactly** the set of leaves a direct diff finds (200 seeded edit sets), with comparisons at most `1 + 2·k·ceil(log2 n)`. Every inclusion proof verifies for every leaf of trees with n = 1..33; changing any single bit of the leaf, any sibling or the index makes verification fail (exhaustive over small trees). **Broken variant:** the 8-bit toy misses a difference on at least one seed (named in the test); the 256-bit version does not on 10,000 seeded edits.
- Hostile input: leaf text is length-capped (64 bytes), non-text refused; the leaf count slider is bounded; an invalid proof index is refused.
- Honesty: Provenance "real SHA-256, truncated display", "toy 8-bit hash is a toy", "anti-entropy as in Dynamo-style stores: from memory, verify against the Dynamo paper", "not a security recommendation".
**Phone.** The 16-leaf tree in `StageFrame minWidth={560}` with sideways scroll; replica compare is stacked vertically at 390; hashes at 4 hex characters stay above 8px.

**`llm-agents-tool-use` · LLM Agents & Tool Use**

**Spec.** An agent is a loop around a model plus tools; the lesson shows the **loop, the context it fills, the permissions around it and the way untrusted text can steer it**, with a deterministic stand-in policy. Nothing here is a real model.

**`randomized-algorithms` · Randomized Algorithms (Las Vegas vs Monte Carlo)**
Track `dsa` · *"Flip coins, get guarantees"* · Builds on: `probabilistic-structures` (registered Tier 4: a soft link, with a one-line recap) · (no domain review)
**Spec.** Opens by quoting `quickselect`'s fence: it showed a random pivot making the *expected* running time linear. This lesson names the two families, and shows the guarantee each gives.
- **Scene 1, Las Vegas: always correct, running time random.** Quicksort with a **fixed first-element pivot** versus a **random pivot**, on an input shape the learner picks (sorted, reverse, "organ pipe", random, **or their own array**), `n` slider (8 to 2,000, computed by counting, never by timing). The fixed pivot on sorted input makes exactly `n(n−1)/2` comparisons. The random pivot is run **1,000 times** (seeded) and the **histogram of comparison counts** is drawn with the **expected value** `2(n+1)Hₙ − 4n` (verify this closed form against a textbook derivation, and the test also checks it against the exact recurrence below) as a `VLine`. The lesson's point: with the random pivot there is no bad *input*, only an unlucky *run*, and the run's bad tail is tiny; an "adversary picks the input after seeing your rule" button defeats the fixed rule and cannot defeat the random one.
- **Scene 2, Monte Carlo: bounded time, random correctness.** A dartboard estimate of `π` (random points in a unit square; fraction inside the quarter circle times 4): the **error versus samples** is plotted on log-log axes with the `1/√n` line (the standard error is `4·sqrt(p(1−p)/n)`, `p = π/4`, computed and drawn as a band); the learner sees four times more darts only halve the error.
- **Scene 3, one-sided error: a primality test.** Using `core/numberTheory`'s Miller-Rabin, the learner picks `n` (presets: `561`, a Carmichael number that fools the plain Fermat test; a prime; `221`; their own up to 10⁹) and runs `k` random-base rounds. For a composite `n`, **the fraction of bases that fail to reveal compositeness (liars)** is computed over *all* bases, and is at most `1/4` (a known bound for Miller-Rabin; verify against a textbook), so `k` rounds err with probability at most `(1/4)ᵏ`. A `Plot2D` of the measured error rate against `k` over 10,000 seeded trials beside the bound. A "no" is certain, a "yes" is probabilistic.
- **Scene 4, converting between them.** A short panel: a Monte Carlo algorithm with a fast verifier becomes Las Vegas by **retrying until the verifier agrees** (shown on the min-cut below); a Las Vegas algorithm becomes Monte Carlo by **stopping after a time budget** and guessing.
- **Scene 5 (advanced tab), Karger's min-cut.** A small graph (6 to 8 vertices, `GraphView`, seeded presets or edited). **Contract** a random edge repeatedly until two super-nodes remain; the edges between them are a cut. **`modular-exponentiation` · Fast Modular Exponentiation**
Track `math` · *"Compute 7^1000000 mod n in 20 steps"* · Builds on: `modular-arithmetic` · (no domain review)
**Spec.** `rsa`, `diffie-hellman` and `primes-factoring` *use* `modPow` as a black box; this lesson is the algorithm and why it is fast. **Toy sizes only, and a Provenance chip says so.**
- **Scene 1, square-and-multiply.** Base, exponent and modulus (`TextField`s through `parseBoundedBigInt`: modulus 2 to 10³⁰, exponent 0 to 10³⁰, base any integer, reduced mod the modulus). The exponent is drawn as a `BitStrip` MSB first. **Left-to-right:** start with the result 1; for each bit, **square** the result, and if the bit is 1, **multiply by the base**; reduce mod `n` after every operation. Each bit lights as it is processed with the running value. A step counter races a **naive repeated multiplication** counter. The headline preset `7^1000000 mod n`: the exponent has 20 bits (7 ones), so the count is **19 squarings and 6 multiplications = 25 modular multiplications** against **999,999** naive (both computed from the exponent, not typed).
- **Scene 2, why reduce at every step.** The unreduced `7^1000000` has `floor(1000000·log10(7)) + 1 = 845,099` digits (computed from `log10`, and the test checks the formula against `BigInt` for small exponents). A `Plot2D` of the digit count of the intermediate value after each bit, with and without reducing: without, the size doubles at every squaring; with, it stays at most the modulus's digits.
- **Scene 3, two scan directions.** `Segmented`: **left-to-right** (above) and **right-to-left** (keep a running power `base^(2ⁱ)`, multiply it in when the bit is 1). Both give the same result; the learner compares what each keeps in memory. A **windowed** variant is named only.
- **Scene 4, the same trick elsewhere.** `a^(p−2) mod p` is the inverse of `a` mod a prime `p` (Fermat); the lesson cross-checks it against `egcd` from `core/numberTheory` for the learner's `a` and `p`. A **Fermat test** panel: `aⁿ⁻¹ ≡ 1 (mod n)` for coprime `a` holds for every prime, and `561 = 3·11·17` passes for **every** base coprime to it (a Carmichael number), so the plain test is fooled (the stronger test is `randomized-algorithms`' topic and named only). The panel is computed by brute force over all bases.
- **Scene 5, a toy honesty note on timing.** The number of multiplications depends on the number of 1-bits of the exponent, so a naive implementation takes *different amounts of work for different exponents*. The lesson shows the counts for a few toy exponents and says that **real implementations are written to take the same time regardless of the secret** (the Montgomery ladder and constant-time code are named only). Nothing here measures or attacks anything.
**Out of scope.** What RSA and Diffie-Hellman are (`rsa`, `diffie-hellman`); Montgomery multiplication, big-integer multiplication cost and constant-time implementation (named); primality testing proper (`randomized-algorithms` names Miller-Rabin; `primes-factoring`); any key generation.

**`chinese-remainder` · The Chinese Remainder Theorem**
Track `math` · *"Rebuild a number from its remainders"* · Builds on: `modular-arithmetic` · (no domain review)
**Spec.** Remainders against several moduli determine a number uniquely inside a bigger range. **Toy sizes only; no keys.**
- **Scene 1, the gears.** Two (or three) rotating gears with `m₁, m₂, (m₃)` teeth (`Segmented` presets and `Slider`s 2 to 30). Each shows the learner's chosen **remainder** (`aᵢ`, a slider bounded to `0..mᵢ-1`). A single tick advances the number `x`; each gear's pointer shows `x mod mᵢ`. The gear dials light up when `x mod mᵢ = aᵢ`, and the first `x` at which **all** light is the answer. Stepping manually or Play; **Sun Tzu's puzzle** preset (`x ≡ 2 mod 3`, `3 mod 5`, `2 mod 7` gives `23`, in a range of 105).
- **Scene 2, build it instead of searching.** The constructive formula: `M = ∏ mᵢ`, `Mᵢ = M / mᵢ`, `yᵢ = Mᵢ⁻¹ mod mᵢ` (via `egcd`/`modInverse`, with the Euclid table), `x = Σ aᵢ·Mᵢ·yᵢ mod M`. Each term is drawn as a bar contributing to `x`, so the learner sees *why it works*: `Mᵢ` is a multiple of every other modulus, so it contributes zero to the other remainders and one (after the inverse) to its own.
- **Scene 3, when the moduli share a factor.** The learner changes the moduli to non-coprime ones (for example `4` and `6`). Remainders are **compatible** iff `a₁ ≡ a₂ (mod gcd)`, and then the solution is unique modulo the **lcm**, not the product; otherwise there is no solution (`x ≡ 2 mod 4` and `x ≡ 3 mod 6` has none: the first forces even, the second odd). The verdict is computed, and the gear scene shows the lights never coincide inside the lcm.
- **Scene 4, residue arithmetic.** Two numbers `u, v` are stored as their residue tuples; **addition and multiplication are done component-wise with no carries** between moduli, and the result is converted back. The result is right as long as it is below `M`; above `M` it wraps (the range overflow, shown). This is the residue number system idea.
- **Scene 5, what it buys.** A toy **CRT speed-up** of a modular exponentiation: compute `c^d mod pq` as two half-size computations mod `p` and mod `q` and recombine (with toy primes like `61` and `53`; the lesson says each half works on numbers about half as long, and for schoolbook multiplication this costs roughly a quarter of the work: verify against a cryptography text, hedged; and that real implementations also guard against computation faults, named only). **Secret sharing** with CRT is named only.
**Out of scope.** Garner's algorithm beyond a one-line mention; RSA itself (`rsa`); fault attacks (not shown); primes and factoring (`primes-factoring`); `modular-exponentiation`'s algorithm (linked: the speed-up scene uses `modPow`).
**Kit.** `core/numberTheory` (`egcd`, `modInverse`, `gcd`, `modPow`, `toyRsa` for the speed-up's primes), `Segmented`, `Slider`, `Bar` (term contributions), gear dials drawn locally as SVG (one user in the tier; reuse the `.scene-*` CSS classes), `CellGrid` (remainder table of `x` against each modulus), `Stat`, `createRecorder`, `Provenance`.

- Misconception: "remainders do not identify a number" and "the moduli just need to be different". They need to be **pairwise coprime** for a unique answer modulo their product. Quiz: for moduli 4 and 6, which pairs of remainders have a solution, and modulo what.

**`leases-fencing` · Leases, Distributed Locks & Fencing Tokens**
Track `arch` · *"A lock that expires, and the token that saves you"* · Builds on: `raft`, `timeouts-deadlines` · **[domain review]**
**Spec.** A client takes a lock with an expiry, then is paused (a garbage-collection pause, a VM stall, a slow disk), the lock lapses, someone else takes it, and the first client wakes up and writes anyway. The lesson shows that **no timeout on the client's side can make that safe**, and what does.
- **Cluster (K3-8).** Nodes: a **lock service** (labelled "one box standing in for a replicated, linearizable store such as a Raft-backed one, see `raft`"), **clients A and B**, and a **storage server** that holds a value. The lock service issues leases with a **TTL** measured on **its own clock** and a **fencing token** that increases by one at every grant. Clocks can differ: each client's local clock has an offset and drift (`Slider`s, in ms and ppm), and a **pause** slider freezes a client for a chosen time at a chosen moment (before the write, or between the lease check and the write).
- **Scene 1, the failure.** The default run: A acquires (token 33, TTL 10 s) and starts a slow job, A is **paused 12 s**, the lease expires, B acquires (token 34) and writes, A wakes believing it still holds the lock and writes with token 33. A `SequenceDiagram` (via `toSequence`) plus a `GanttLanes` (lease bars, a hatched paused bar) show it; storage's value history shows B's write overwritten by A's stale one. A **mode** `Segmented` follows.
- **Modes.** (a) **No fencing:** the storage server accepts everything: the stale write is applied. (b) **Check the lease before writing:** A looks at its (local) clock and the lease expiry just before the write; the learner puts the pause **after the check** and the stale write goes through anyway (a check-then-act race); a second case where A's clock runs slow and it believes it still holds the lease. (c) **Fencing tokens:** the storage server remembers the **highest token it has applied** and rejects any lower one: A's write with 33 after B's 34 is refused with a visible "rejected: stale token 33 < 34". (d) **Non-monotonic tokens** (a `Toggle` "lock service issues random tokens"): fencing no longer protects, because "lower" means nothing.
- **Scene 2, renewals and TTL.** A renewing client extends its lease every `TTL/3` with a heartbeat; a pause longer than the TTL lapses it regardless, and a **partition** between A and the lock service stops renewals while A still reaches storage. The learner sets TTL (1 to 30 s), heartbeat interval and pause, and a table of outcomes per mode is **computed by running the sim** over the grid of settings.
- **Scene 3, what fencing needs.** A short panel: the **storage server must take part** (check the token); a resource that cannot check tokens (an external API) cannot be fenced by this scheme, so the lesson names alternatives (idempotent writes, conditional writes or compare-and-set against a version) without teaching them. Leases are for **efficiency** (avoid duplicate work) or **correctness**: for efficiency a lapsed lease is harmless; for correctness it needs fencing. The `Redlock` debate is named and the lesson says it takes no side beyond the fencing argument (verify against the published posts by Kleppmann and by the Redlock author before quoting any claim).
**Out of scope.** The consensus algorithm behind the lock service (`raft`); timeout selection and propagation (`timeouts-deadlines`); the distributed cron that uses a lease (`job-scheduling`); clock-synchronisation protocols (`physical-clocks-skew`); ZooKeeper, etcd or Chubby API details (named only).

**`job-scheduling` · Background Jobs, Delayed Queues & Distributed Cron**
Track `arch` · *"Work that runs later"* · Builds on: `leases-fencing` · **[domain review]**
**Spec.** Three questions: *when* does a job run, *how many times*, and *on which replica*. `message-queues` and `poison-messages-dlq` cover queues and dead letters; `leases-fencing` covers the lease; this lesson puts them to work.
- **Scene 1, a delay queue and a timing wheel.** The learner enqueues jobs with a delay (`TextField` seconds or chips). A **hashed timing wheel** of 8 slots with a 1 s tick turns a pointer; each job sits in the slot `(due tick) mod 8` with a **rounds** count (`floor(delay / 8)`); a slot fires the jobs whose rounds reach 0. The same jobs go into a **sorted queue (a heap)** for comparison. The wheel fires jobs within the tick of the heap's order and **not in exact due-time order inside one tick**; the lesson computes and shows the difference, and why a wheel gives `O(1)` insert at the price of tick granularity. (The wheel's resolution and the "Kafka and Netty use hashed wheels" remark are from memory: verify against their docs.)
- **Scene 2, at-least-once.** Workers pull jobs from a queue with a **visibility timeout**: a taken job is invisible for `T` seconds and reappears if not acknowledged. The learner kills a worker mid-job or makes a job run longer than `T`: it **runs twice**. A **retry policy** panel (max attempts, base delay, cap, **jitter on/off**) uses `delay = random(0, min(cap, base · 2^attempt))` for full jitter (verify the name against the AWS architecture blog post on retries with jitter) and shows retries from many failing jobs piling up in lockstep without jitter and spreading with it. After the max attempts a job goes to the **dead-letter queue** (`poison-messages-dlq`). An **idempotency key** toggle makes the second run a no-op (`idempotency-keys`).
- **Scene 3, distributed cron.** Three scheduler replicas each hold the same job (`0 * * * *`) and each tries to fire it at the top of the hour. **Mode (a) every replica fires:** the job runs three times. **(b) leader election by lease:** only the lease holder fires; the learner **kills the leader** and watches the gap before another takes over (a missed run, or a double run if the old leader was only paused), and with **fencing** the paused ex-leader's late fire is rejected (`leases-fencing`). **(c) run-once by dedupe key:** every replica tries to insert a row `(job, scheduled time)` with a unique constraint, exactly one wins, and no leader is needed. A `Gantt` with the **calendar axis** (K3-12, UTC) shows a day of fires per replica.
- **Cron expressions.** A field `TextField` for a five-field expression (restricted to `*`, lists, ranges and steps in each field; parsed by a hand-written parser through `core/parse`, never `eval`). The next five fire times are computed. A **day-of-month versus day-of-week** preset (`0 0 13 * 5`): when both fields are restricted, common cron implementations fire when **either** matches (the Vixie cron rule: verify against `man 5 crontab`); the lesson shows the surprising result. A **daylight-saving** note: a local-time schedule at 02:30 does not exist on a spring-forward day and happens twice on a fall-back day, behaviour differs by implementation (verify), which is why the lesson schedules in UTC and says so.
**Out of scope.** Lease and fencing mechanics (`leases-fencing`); queue semantics and delivery guarantees in general (`message-queues`, `exactly-once-myth`); dead-letter handling beyond naming it (`poison-messages-dlq`); workflow engines and DAG orchestration (named; `etl-orchestration` covers pipelines).
**Kit.** K3-8 `createCluster` (replicas, workers, a queue node, crashes, pauses, clock skew), `checkInvariants`, `forSeeds`, `GanttLanes` (K3-12 calendar axis and `hideEmptyLanes`, K3-10 `barAt`, K3-11 instants for enqueue and fire), `LogStream`, `SequenceDiagram`, `core/parse` (a local cron parser in `model.ts`, one user), `TextField`, `Slider`, `Segmented`, `Toggle`, `Stat`, `Provenance`.

- Watch: a job waiting `--dim`, running `--hi`, done `--ok`, a **duplicate run** `--bad`, a retry `--orange` (a category), the DLQ `--violet`; the timing wheel's pointer `--hi`, slot rounds `--info`; a missed fire `--bad` hatched; the dedupe key `--violet`.
- Misconception: "a cron job on three servers runs once" and "at-least-once means exactly once if I retry carefully". Quiz: a worker takes a long job and the visibility timeout expires: what happens, and which of idempotency or a bigger timeout is the real fix.
- Correctness: **invariants over 200+ seeded schedules** (worker and replica crashes, long pauses, clock skew of up to a stated number of seconds between replicas, duplicated and delayed messages): **J1 (safety, with the dedupe key)** every scheduled `(job, time)` takes effect **at most once**; **J2 (at-least-once, a liveness property stated separately, under fair schedules that eventually let a replica run)** every scheduled fire executes **at least once** unless it exhausts its retries and lands in the DLQ; **J3** no job is lost: it is always in exactly one of waiting, running, done or the DLQ. The cron parser equals a **brute-force minute-by-minute matcher** over a year of minutes for 200 seeded expressions (including the day-of-month/day-of-week OR rule), and the timing wheel fires every job at the tick `ceil(due / tick)` (never early, at most one tick late) against the heap oracle. **Broken modes must violate on a named seed:** mode (a) violates **J1** on every schedule (hand-built: three replicas, one fire time); the leader-by-lease mode **without fencing** violates **J1** on a seed in which the leader is paused past its lease; the visibility-timeout mode without an idempotency key violates **J1** when a job outruns `T`. The pinned seed and trace appear on screen.
- Hostile input: delays and times are bounded; a cron field outside its range (`61` minutes), an empty field or more than five fields is refused with the reason; a step of 0 (`*/0`) is refused; more than 40 queued jobs refuses the next with a message.

**`transactional-outbox` · Transactional Outbox & Dual Writes**
Track `arch` · *"Write the DB and the event, atomically"* · Builds on: `distributed-transactions` (registered Tier 4: soft link, one-line recap), `change-data-capture` (wave 6) · **[domain review]**
**Spec.** Quotes the fence: `distributed-transactions` taught sagas and two-phase commit; `change-data-capture` shows a log reader. This lesson is the **dual-write bug** and the **outbox** fix, nothing more.
- **Scene 1, the bug.** A service handles "place order" with two steps against two systems that cannot commit together: **(1)** insert the order in the database, **(2)** publish `OrderPlaced` to a broker. A `Segmented` picks the **order of steps** (DB first or publish first). A **Crash point** row has a button before each step boundary (before step 1, between 1 and 2, after 2 before the response), and the learner clicks one. The outcome is computed by running the steps: DB first with a crash between them gives an **order with no event** (downstream never learns: a lost event); publish first with a crash between gives an **event with no order** (a ghost); a **publish that fails after the DB commits** is the retry dilemma. A table of **every crash point x both orders** is generated by exhaustively running the model (not typed) with each cell's outcome.
- **Scene 2, the outbox.** The service writes the order **and** a row in an `outbox` table **in one local transaction** (a real atomic unit: the toy DB's `transactions-acid` behaviour). A **relay** (a separate process) reads unsent outbox rows, publishes them, and marks them sent. The learner crashes the service before commit (neither row exists), after commit (both exist; the relay delivers later), and the relay between publish and mark (the event is published **twice**). A **consumer dedupe** `Toggle` (an inbox table or event-id check, linked to `idempotency-keys` and `exactly-once-myth`) makes the second delivery a no-op.
- **Scene 3, the polling trap.** Two concurrent transactions get outbox ids 41 and 42; **42 commits first**. A relay that polls `WHERE id > last_seen` reads 42, advances to 42, and **never sees 41** when it commits a moment later. The learner interleaves the two commits (`Segmented` of orderings) and the missed event is produced by the model. Mitigations are named: read from the **log** (`change-data-capture`), or poll with a safety margin and re-scan (named, hedged), or use a monotonic commit order the database guarantees (verify against your database's docs).
- **Scene 4, compared.** A table (a `.data-table`) of **dual write**, **outbox with polling**, **outbox with CDC**, **two-phase commit across DB and broker** (needs both to support it; blocking on coordinator failure: from `distributed-transactions`), and **listen to your own events** (named): what each guarantees, its cost and its failure, with the guarantees **computed from the invariant runs** below, not typed.
**Out of scope.** The CDC reader (`change-data-capture`); saga compensation and 2PC mechanics (`distributed-transactions`); broker internals (`kafka-partitioned-log`); event sourcing (`event-sourcing`) is a different pattern named in one line; idempotency key design (`idempotency-keys`).
**Kit.** K3-8 `createCluster` (nodes: service, database, relay, broker, consumer; `crash` at any step, `dropNext`), `checkInvariants`, `forSeeds`, `toSequence` + `SequenceDiagram` (`lost` messages), `CellGrid` (DB table, outbox table, consumer state; K3-16 row tone for sent/unsent), `Segmented`, `Toggle`, `ChipButton`, `.data-table` with `SortTh` (K3-4) optional, `Stat`, `Provenance`.
**AC.**
- Watch: a committed order `--ok`; an event published with no committed order (a ghost) `--bad`; a committed order whose event never comes (a lost event) `--bad`; a duplicate delivery `--orange` (a category: duplicates are expected); an unsent outbox row `--hi`, sent `--ok`; the atomic boundary around the two writes `--violet`.
- Misconception: "I will just publish right after the commit and retry if it fails" and "outbox gives exactly-once". It gives **at-least-once publishing**, so the consumer must be idempotent. Quiz: the service crashes after the DB commit and before the publish: with a dual write what is lost, and with an outbox what happens at restart.
- Correctness: **invariants over 200+ seeded schedules** with a crash injected at every step (including inside the relay) and duplicated and delayed messages: **O1 (no ghost)** every event the consumer sees corresponds to a committed order; **O2 (no loss, a liveness property stated separately, checked once the system is quiesced after restarts)** every committed order's event is eventually published at least once; **O3** with consumer dedupe, each event's effect is applied **exactly once**. The outcome table of scene 1 equals an independent hand-written table of the six cases. **Broken modes must violate on a named seed/schedule:** DB-first dual write violates **O2** (hand-built: crash between the commit and the publish); publish-first violates **O1** (crash after publish, before commit); the outbox **without** consumer dedupe violates **O3** when the relay crashes between publish and mark; the `id > last_seen` poller violates **O2** on the two-transaction interleaving above. Pinned seeds and traces are shown.
- Hostile input: order amounts are bounded integers; a crash button is offered only at real step boundaries; more than 30 orders refuses the next with a message.
- Honesty: Provenance "simulated (seed N)", "toy database: commit order and ids modelled, not a real engine"; the commit-order caveat for sequences is "from memory, verify against your database's docs".
**Phone.** Sequence diagram in a `WideRegion`; the crash-point row wraps; the tables stack.

**`fanout-feeds` · Fan-out on Write vs Read (News Feeds)**
Track `arch` · *"Push or pull the timeline"* · Builds on: `message-queues` · (no domain review)
**Spec.** A post, some followers, a feed: where does the work happen, at write time or at read time?
- **Population.** A seeded population of 2,000 users (labelled a scaled-down model) with a **heavy-tailed follower distribution** (a few users with thousands, most with tens: Zipf-like, computed from a seed) and a follower graph. A follower count slider picks **one author** (10 to 100,000 followers: the large end is computed in work units, not instantiated).
- **Scene 1, push (fan-out on write).** The author posts. A fan-out job writes the post id into **every follower's inbox** (`CellGrid`, one row per follower; K3-16 row tone fills as writes land). Write cost = followers (inbox inserts); read cost = 1 inbox read. A `Slider` for **fan-out workers** and a per-insert time gives the **time until the last follower can see the post** (computed), and a queue (`message-queues`) of fan-out tasks drains.
- **Scene 2, pull (fan-out on read).** The post is stored once. A reader's feed is built at read time by **merging the latest posts of everyone they follow**: with `F` followees and a page of `N = 20` it is a `k`-way merge of sorted lists (a heap of size `F`, `F` initial entries plus `N` pops: about `F + N·log F` operations, computed and shown with the actual number). Write cost = 1; read cost grows with `F`.
- **Scene 3, the hybrid.** A `Slider` **celebrity threshold** `T`: authors with more than `T` followers are **pulled** (merged into the reader's feed at read time), everyone else is **pushed**. The read path merges the reader's inbox with the recent posts of the followed celebrities. The learner sets the **read-to-write ratio** and `T` and sees **total work per hour** for push, pull and hybrid (stacked `Bar`s, computed from the seeded population and the traffic mix), the **crossover** read:write ratio where push beats pull, and the **worst-case post latency** (the celebrity push to 100,000 inboxes versus the hybrid's 0).
- **Scene 4, details that bite.** A short stepper: inactive users (skip the push for users who have not logged in within a window, backfill on return), deletes and edits (the post is gone from 100,000 inboxes: a second fan-out), ordering (by time, ties by id), and a **ranked** (not chronological) feed's need to see candidates at read time. Named, not simulated beyond a one-line effect each.
**Out of scope.** Ranking models (`recommender-systems`); the message queue itself (`message-queues`); storage of timelines and sharding (`sharding`, `hot-keys-skew`); notification delivery.
**Kit.** `CellGrid` (inbox rows, K3-16 `rowDecor` rails), `Bar` (`segments` for push/pull/hybrid work), `Plot2D` (cost against follower count on log axes; `VLine` at `T`), `Slider` (log steps, `format`), `Segmented`, `useTickSim` (K3-2) for the fan-out drain, `core/random`, `core/stats` (a Zipf helper local to `model.ts` unless `hot-keys-skew` in this batch needs the same: **two users in one batch means stop and ask for the kit round, not copy**: see Kit gaps below), `Stat`, `Provenance`.
**AC.**
- Watch: push work `--info` (an inbox write), pull work `--violet` (a merge read); the cheap side `--ok`, the costly side `--bad` per scenario's computed comparison; a celebrity author `--hi`; an inbox row filled `--ok`, empty `--dim`; a stale feed (not yet fanned out) `--orange`.
- Misconception: "push is always better because reads are cheap" and "pull is always better because writes are cheap". It depends on the read:write ratio and on the **follower distribution**: the celebrity case breaks push, the heavy reader breaks pull. Quiz: a user with 5 million followers posts once an hour and each follower reads daily: which strategy does the work, and where.
- Correctness: independent oracle is a **brute-force feed**: collect all posts of all followees, sort by `(time, id)`, take the first `N`. For 200 seeded populations, posts and readers, the **push, pull and hybrid feeds equal the brute-force feed exactly** (same posts, same order, no duplicates, none missing). The work counts equal an independent counter (inserts for push, heap operations for pull) and the crossover ratio equals the analytic `followers / (F + N log F)` ratio the lesson prints. Deletes: after a delete no strategy shows the post. **Broken variant:** a hybrid that forgets to merge celebrity posts is missing posts for readers who follow a celebrity, and the test detects it against the brute-force feed.
- Hostile input: slider-bound everything; a threshold of 0 (everyone is a celebrity) and of infinity (no one) are allowed and shown as pure pull and pure push; the follower count input is bounded and computed (not allocated) above 20,000.
- Honesty: Provenance "scaled-down seeded population, work in abstract units", "real feeds also rank, filter and cache; companies' own designs differ: no real company's numbers are used".

**`hot-keys-skew` · Hot Keys & Data Skew**
Track `data` · *"One celebrity melts one shard"* · Builds on: `sharding` · (no domain review)
**Spec.** Sharding spreads *keys* evenly; skew is that *traffic* is not spread evenly across keys. `sharding` taught how keys are placed and `consistent-hashing` how placement changes; this lesson assumes placement (hash of the key mod 8, stated) and studies load.
- **Scene 1, the melt.** 8 shards (`CellGrid` bars or `Bar`s with per-shard capacity lines) and 1,000 keys with a **Zipf popularity** (`Slider` exponent `s` from 0 to 1.5; `s = 0` is uniform). A seeded request stream (K3-2) fills the bars. A **total utilisation** slider (10% to 100% of aggregate capacity) shows the key point: with `s = 1` the **hottest shard can saturate while total utilisation is only about half**, because the hottest key alone carries `1 / Hₙ,ₛ` of all traffic (about 13% for `n = 1,000, s = 1`, computed: `H₁₀₀₀ ≈ 7.485`), so the hottest shard sees at least `p₁ + (1 − p₁)/8` of the load. The stats row prints **max shard load / mean**, the **utilisation at which the first shard saturates** (computed: `(1/8) / (p₁ + (1 − p₁)/8)`) and which key is the culprit.
- **Scene 2, mitigations.** Buttons that you apply to the hot key(s), each with its parameter and cost. **Key salting:** append a random suffix `0..m−1` to the hot key's **writes** so they spread over `m` shards; a **read** must now **scatter-gather** all `m` (read fan-out `×m`, shown). **Splitting the range** of a hot key space. **A cache in front** (a hit-ratio slider absorbs reads before the shard sees them; useless for writes). **Replicating hot reads** to several shards. **Coalescing** duplicate in-flight requests (named, as the idea behind a "stampede" defence, whose lesson is later). A `Slider` for the **read:write mix** shows which mitigation helps which side: salting fixes write skew and costs reads, a cache fixes read skew and does nothing for writes.
- **Scene 3, find the hot keys.** A heavy-hitter detector (the Count-Min Sketch of `count-min-heavy-hitters`, linked, wave 4) flags the top keys from the stream with a memory budget slider; the learner sees the flagged set **miss** a hot key when the sketch is too small. Detection feeds the mitigation: only flagged keys are salted.
- **Scene 4, hot in time.** A **burst** `Toggle` moves the hot key over time (a celebrity event): a static split made for yesterday's hot key does nothing for today's. The bars show it.
**Out of scope.** How keys are placed (`sharding`, `consistent-hashing`); the sketch's internals (`count-min-heavy-hitters`); cache stampede (a wave 10 lesson, named only); multi-tenant noisy neighbours (`multi-tenancy`, wave 10, named).
**Kit.** `Bar` (per-shard load with a capacity `marker`), `CellGrid` (K3-16 `rowDecor` for shard rows) or `Plot2D` `Bars` with the K3-1 per-bar tone, `useTickSim` (K3-2), `core/random` (`mulberry32`, `weightedPick`), `core/hash` (`hash32`), `core/stats`, `Slider`, `Segmented`, `Toggle`, `ChipButton`, `Stat` (K3-3), `Provenance`.
**AC.**
- Watch: a shard under its capacity `--ok`, one past it `--bad`, the hottest shard `--hi` outlined; the hot key `--orange` (a category: a key, not an error); salted sub-keys `--violet`; cache-absorbed requests `--info`; a sketch-missed key `--dim` struck.
- Misconception: "hash sharding spreads load evenly" and "if total utilisation is 50% we have headroom". Hashing spreads **keys**, not **requests per key**. Quiz: total load is half of cluster capacity and one shard is dropping requests: what is the likeliest cause, and what does salting cost the readers.
- Correctness: the shard load shares equal an independent count of the seeded stream; **conservation:** shard loads sum to the total number of requests in every scene and with every mitigation (salting redistributes, a cache removes only the cached reads, which the stats show); the analytic hot-key share `1 / Hₙ,ₛ` equals the measured share over 100,000 seeded requests within a Monte Carlo tolerance; the saturation utilisation formula matches the sim's measured first-saturation point; after salting with `m` suffixes the hot key's per-shard write share is `p₁/m` within tolerance and read fan-out is exactly `m`; for **uniform** traffic the max/mean ratio is close to the balls-into-bins expectation (verify the form `1 + sqrt(2·ln(k)·k/n)`-style against a reference before showing any closed form; otherwise show only the measured value). **Broken variant:** salting applied to reads as well as writes without gathering returns partial data for a salted key; the test detects missing results against a single-node oracle.
- Hostile input: all inputs are sliders or chips; the sketch memory slider has a minimum; `m` is bounded 2 to 8.
- Honesty: Provenance "seeded request stream (seed N)", "Zipf is a model of popularity, real skew varies", "8 shards, mod placement"; the `1/H` figure is computed on screen, not asserted.
